## 0. 这次修订解决什么（Why）

v0.4 写于 2026-09-21，当时**渲染层还在吃 demo 数据**，主进程与界面之间是断的。
这意味着 v0.4 里所有关于「数据怎么来、写操作怎么落库、只读怎么拦」的描述
**都还是设计意图，不是已验证事实**。

本轮把这些意图接成了真实链路，并在真机上跑了 25 项断言。结果是：

- **6 项设计意图被证实**（按原样实现即可，无需改设计）
- **4 处设计与实现出现偏差**（其中 1 处是安全相关，必须写进 PRD 约束）
- **1 项指标口径需要收敛**（冷启动子预算的实测基线）
- **2 项开放问题可以关闭**

> **给工程的一句话**：本轮**没有新增功能需求**，也不扩大范围。
> 全部修订都是「把已实现的东西写准」，避免后续开发照着过时描述返工。

## 2. 🔴 必须并入的 4 处修订

### 2.1 R13：只读拦截的安全层边界（修订 §6.1.6）

**性质**：🔴 安全修订（原描述不够强，容易被误读）

v0.4 §6.1.6 已按 R2 写明用 AST 白名单。本轮真机验证补一条**必须写死的边界**：

> **只读拦截的唯一安全层是主进程的 AST 白名单。UI 置灰、禁用按钮、
> 前端校验都不是安全层 —— 它们能被快捷键、粘贴、命令面板绕过。**

真机验证方式：在渲染层**直接调用** `queryRun({ sql: 'DELETE FROM ...' })`，
绕过一切 UI 状态，请求仍然被主进程拒绝（`READ_ONLY`）。
同一条连接上的 `SELECT` 正常放行。

**给工程的约束**：
- 任何新增写操作入口（未来的表设计器、导入向导、命令面板命令），
  **必须**经过 `checkReadOnly()`，且该调用必须在主进程
- 不要在渲染层做"只读判断"来提前 return —— 那会制造虚假安全感

### 2.2 R14：safeStorage 异步解密返回对象（修订 §10 / §10.1）

**性质**：🔴 正确性修订（涉及凭据安全，最高优先级）

**实测事实**：Electron 44 的 `safeStorage.decryptStringAsync()` 返回的是

```ts
{ result: string; shouldReEncrypt: boolean }
```

**不是**字符串。同步版 `decryptString()` 才返回字符串。

**踩坑记录（必须留在文档里）**：本项目最初按旧签名（`Promise<string>`）
定义接口，**单测替身也照着同样的错误签名实现** —— 于是 197 行单测全绿，
真机一跑密码变成对象传给 mysql2，报 `The "data" argument must be of type string`。

> **这是本轮最值钱的教训，写进 PRD 作为长期约束：**
> **测试替身不能照着被测代码的假设来实现。** 那样它只会跟被测代码一起错，
> 测试看起来在保护你，实际在掩盖 bug。
> **凡是对外部 API 返回形态的假设，都必须有一条真机断言看着它。**

**PRD 新增约束（§10.1 追加）**：

1. 解密结果必须经 `normalizeAsyncDecrypt()` 归一化，同时兼容「对象」与「裸字符串」
   两种形态（旧版 Electron 与历史密文都要能解）
2. `shouldReEncrypt === true` 表示系统密钥已轮换 → 按官方语义**再解密一次**，
   并触发上层把密文用新密钥重新加密落盘（`ConnectionStore.replaceCipher()`）。
   **不做这一步，老密文会永久停留在被轮换掉的旧密钥上**，违背密钥轮换的安全意图
3. 真机门禁须包含 safeStorage 契约断言，防 Electron 再升级时签名悄悄变

### 2.3 R15：渲染层产物的打包约束（新增 §7.4）

**性质**：🔴 工程修订（影响打包配置，不写会重复踩）

Electron 用 `file://` 加载渲染层产物，与常规 Web 部署有两处必须不同的配置：

| 约束 | 不做会怎样 |
|---|---|
| Vite `base` 必须为 `'./'`，且是**顶层字段** | 默认 `/assets/xxx.js` 在 `file://` 下解析到**磁盘根目录**，JS 根本没加载。写进 `build.base` **不报错但静默失效** |
| 产物 HTML 必须去掉 `crossorigin` 属性 | file:// 下带 crossorigin 的模块脚本被拒绝加载 |
| CSP 只在**构建期**注入（`apply:'build'`） | dev 模式下会挡掉 Vite HMR 客户端与 react-refresh 内联脚本 → dev 白屏 |
| CSP 的 `style-src` 必须含 `'self'` | 只写 `'unsafe-inline'` 会拦掉构建抽离的独立 `.css` → 有结构无样式 |

> **这类故障的迷惑性值得单独记一笔**：渲染层 JS 完全没加载时，
> **主进程 IPC 全部照常工作**。如果验证方式是"调接口看返回"，
> 会得到 100% 通过的错误结论。
> **真机门禁必须断言 DOM 真的渲染出来了**，不能只断言接口通。

### 2.4 R16：排序状态的所有权（修订 §6.3）

**性质**：🟡 语义澄清

v0.4 已按 R10 写明"排序必须在服务端执行"（因 BIGINT 字符串化）。
本轮发现配套的**客户端状态所有权**没说清，导致实现出错：

> 排序状态属于**客户端**，服务端只负责按给定的 `ORDER BY` 返回数据。
> 「因排序变化触发的重新拉取」**不得清空排序状态**；
> 只有「切换到另一张表」才重置。

**踩坑**：`loadTable` 无条件 `setSorts([])`，而排序触发的重拉走同一个函数，
于是服务端刚排好、客户端立刻把状态清了 —— 表头箭头消失，
三态循环（ASC → DESC → 清除）永远走不完第二轮。

## 4. ⬜ SQL 编辑器：下一个里程碑（需评审后开工）

这是**当前唯一的 P0 未开工项**，也是核心闭环「连接 → 定位表 → 查改数据」
里唯一还缺的能力（用户故事 US-3 依赖它）。

### 4.1 为什么现在必须评审

不是因为工作量大，而是因为它**同时踩两条硬约束**：

| 约束 | 数值 | 风险 |
|---|---|---|
| S2 首屏 bundle | ≤ 1.5 MB 未压缩（当前 271 KB） | CodeMirror 6 + sql-formatter + MySQL 方言包是**最大单点增量** |
| §7 SQL 编辑器首字符输入延迟 | ≤ 16 ms | 懒加载的首次载入会打破这项，需要明确"首次 vs 后续"口径 |

### 4.1 评审结论（2026-09-23 拍板，E1~E4）

> 拍板依据不是估算，是**在本仓库实测的打包体积**（esbuild 打同一份 import 集合）。
> 结论先给：四项建议**三项照原样通过，一项被实测推翻**。

**实测基线（本机，esbuild bundle）**

| 组合 | 未压缩 | minified | min+gzip |
|---|---|---|---|
| 精简集（编辑器 + MySQL 方言 + 补全 + 括号 + 语法高亮，不含 search/fold） | **782 KB** | 385 KB | — |
| 全集（再加 search / fold / 活动行高亮 / 矩形选区） | **844 KB** | 417 KB | **137 KB** |
| 单项：`@codemirror/view` 源码 | 481 KB | — | — |
| 单项：`@codemirror/state` | 143 KB | — | — |
| 单项：`@codemirror/lang-sql` | 52 KB | — | — |
| 当前首屏 bundle | **271 KB** | — | 87 KB |

---

#### E1 懒加载边界 —— ✅ 通过（单个 lazy chunk）

「编辑器 + MySQL 方言 + 补全 + 括号匹配」作为**一个** `import()` chunk，
首次打开查询标签时载入。**不要拆细**：

- 数据集显示精简集与全集只差 62 KB —— 细拆省不下什么
- CodeMirror 各子包互相依赖（view 依赖 state / language 依赖 lezer），
  细拆只会产出多个**必须同时加载**的 chunk，等于白交多次请求开销
- 用户是要用才打开，chunk 内没有可延迟的冷代码

**不做预加载**（不用 `<link rel=modulepreload>`）：首屏 271 KB 已经很轻，
为省一次 300ms 内的懒加载而把它塞回首屏，是拿 S2 的硬约束换一个没人感知的优化。

#### E2 体积预算 —— 🔴 **原建议 400 KB 未压缩不成立，改为两级预算**

实测**精简集就已经 782 KB 未压缩**，原「≤400 KB」在"未压缩"这个口径下
**物理上不可达** —— 光 `@codemirror/view` 源码就 481 KB。
这不是实现得不够瘦，是 400 KB 这个数字从一开始就定错了口径：
它把「min+gzip 后的传输体积」的直觉套到了「未压缩源码」上。

改为**两级预算**，各管各的风险：

| 级别 | 预算 | 实测 | 管的风险 | 超出怎么办 |
|---|---|---|---|---|
| **lazy chunk 传输体积** | **≤ 150 KB min+gzip** | **123 KB** ✅ | 懒加载 ≤300ms（E3） | 砍 sql-formatter → 砍 search → 砍 fold |
| **首屏 —— CodeMirror 部分** | **0 KB**（一个字节都不许进） | **0 KB** ✅ | S2 首屏 ≤1.5MB | 超了就是懒加载没生效（bug，不是权衡） |
| **首屏 —— 筛选/详情业务逻辑** | **≤ 20 KB** | **+16 KB**（271→288） ✅ | 同上 | 这钱花得值：筛选器是首屏功能 |

**首屏增量的实测拆解**（原估「≤5KB」是拍脑袋，实测推翻后按实况修正）：

- CodeMirror 部分 **0 KB** —— Vite 的 dynamic import 只在首屏留 chunk 地址表
  与 `__vitePreload` 垫片，编辑器本体从不进首屏。**这条已写进门禁断言**
  （`scripts/check-bundle.mjs`：首屏产物里出现 `cm-editor` / `GROUP_CONCAT` 即失败）
- 剩下的 +16 KB 是 **`core-filter` + `core-sql-editor/facts`** —— 筛选器与详情面板
  都是首屏功能，这笔开销是应得的，不是泄漏

> 🔧 **为此做的一个拆分**：`tableFacts()` / `formatCount()` 原本在
> `core-sql-editor/index.ts` 里，而那个文件还带着 SQL 关键字表与函数表。
> 详情面板（首屏）一引就把整张表拖进来了 —— 实测多付 15KB。
> 拆成独立子入口 `core-sql-editor/facts` 之后，首屏只为这两个函数付费。
>
> ⚠️ **顺带踩到一个 Vite 坑**：`resolve.alias` 是**前缀匹配**的，
> `@dbstudio/core-sql-editor/facts` 会命中 `core-sql-editor` 规则被拼成
> `.../src/index.ts/facts`（→ `ENOTDIR`）。必须用**数组形式**并把
> 带 `$` 的 exact 正则规则排在最前。

**sql-formatter 决策**：v1 **不引入**。它不在上表的实测里（未安装），
但作为纯锦上添花的依赖，在预算已经偏紧的前提下不值得为一个 formatter
多付一个依赖的体积与维护成本。`Cmd+Shift+F` 需求降级为「保留快捷键位，
v1.1 再评估」。

#### E3 首字符延迟口径 —— ✅ 通过（不计入），但补一条硬要求

懒加载 chunk 的**首次**下载+解析时间**不计入** §7 的「首字符输入延迟 ≤16ms」。
理由：16ms 约束管的是「输入响应感」，而懒加载发生在用户**敲第一个字符之前**
（打开标签 → loading → 可输入），两者不在同一时间轴上。

但补偿一条硬要求，否则这个"不计入"会变成无限豁免：

- **chunk 载入 ≤ 300 ms**：实测 **0.6 ms**（预热生效后走模块缓存）
- **必须有 loading 态** —— 不允许点了查询标签后界面无反馈
- **可输入后的首字符延迟仍需 ≤16ms**（这才是原约束的本意）

> 🔧 **实现过程中修正的两个误判**（都写进门禁注释了，防止后人重犯）：
>
> 1. **口径**：E3 管的是「**chunk 载入**」，不是「编辑器可见」。
>    后者还含 `new EditorView()` 的初始化（建 DOM + Lezer 解析 + 量字体），
>    实测 323ms —— 那是 CodeMirror 的固定成本，与懒加载策略无关，
>    且已被 loading 态覆盖。混淆两者会让优化方向跑偏。
> 2. **预热时机**：先用 `requestIdleCallback`，结果**完全没生效**
>    （门禁报 `预热=false`）。原因是启动阶段连接列表 IPC + schema 反序列化
>    + 树渲染会连续占满主线程好几秒，"空闲"迟迟不来。改 `setTimeout(0)`
>    后立刻生效 —— 首屏 DOM 已提交，抢不到用户的渲染时间。

#### E4 补全数据源 —— ✅ 通过（复用 schema 缓存），并加两条约束

补全元数据**只来自已有的 schema 缓存**（渲染层 `App` 里的 `schemas` state，
源头是 `SessionRegistry` 的磁盘快照 + 内存快照）。**不得**为补全新开查询链路，
**不得**现查 `information_schema`。

两条补充约束：

1. **补全候选构建必须是纯函数**，进 `core-sql-editor` 并配单测 ——
   这样「延迟 ≤100ms」这个验收不依赖真机，纯逻辑就能测
2. **候选集要限量**：库/表/字段总数可能上万，补全必须做前缀过滤 + 上限截断
   （默认 ≤200 条），否则大库下拉会卡住输入

## 附：本轮验证方法论（建议写进团队约定）

1. **替身不能照着被测代码的错误假设实现** —— 那样它只会跟被测代码一起错。
   对外部 API 形态的假设，必须有真机断言看着
2. **"调接口全通" ≠ "页面能用"** —— 渲染层 JS 没加载时主进程 IPC 照样全绿。
   真机门禁必须断言 DOM 真的渲染出来
3. **e2e 失败先 dump 现场**（`#root` innerHTML + 控制台错误），
   别对着一句 `waitForSelector timeout` 猜 —— 本轮 4 个 bug 有 3 个靠 dump 才看清
4. **断言语义，不断言实现细节** —— 硬编码密文字面值的测试，
   在替身换 salt 格式时全红，而产品行为其实完全正确
