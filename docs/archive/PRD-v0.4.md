## 一、问题定义（Problem Statement）

### 1.1 用户是谁

一个**同时写业务代码、又要自己改数据**的开发者。他不是 DBA，不需要权限体系、审计、监控大盘；他是全栈 / 后端 / 独立开发者，每天要反复做这几件事：

- 在多个环境（本地 / 开发 / 测试 / 生产）之间来回切，查同一张表
- 写完 SQL 看结果，发现写错了改一改再跑
- 找到几行数据，改成想要的值
- 把查询结果导出给同事，或把运维给的 Excel 灌进库里
- 看一眼表结构，确认某个字段是什么类型、有没有索引

**关键特征**：他是**间歇性使用**。一天打开几十次，每次停留 30 秒到 5 分钟，中间夹着 IDE、浏览器、终端。工具必须"切过去就能干活，干完就切走"。

### 1.2 他现在痛在哪

| 痛点 | 具体表现 | 代价 |
|---|---|---|
| **启动与响应慢** | Navicat 冷启动 5-8s；DBeaver 常驻 500MB-1GB 内存 | 打断心流，干脆改用命令行 |
| **网格一编辑就心慌** | Navicat 网格编辑后到底提交没提交，反馈不明确；Navicat 17.1.3 曾出现"把整行置 NULL 而非仅改选中单元格"的严重 bug | 不敢在生产库用 GUI 改数据，退回写 UPDATE 语句，更慢更危险 |
| **大表就卡** | 打开一张千万行表，Navicat 分页翻页偏慢；DBeaver 默认全量加载导致滚动卡顿 | 只能写带 LIMIT 的 SQL，失去可视化浏览能力 |
| **找表靠眼睛扫** | 一个库几百张表，树里翻半天 | 每次找表 20-30 秒 |
| **快捷键太少** | Navicat 被普遍吐槽 "very few shortcut keys"，且大量操作只用 Ctrl 不用 Cmd | 全程鼠标，手不离键盘的习惯被打断 |
| **原生感缺失** | Navicat 是跨平台自绘 UI，在 Mac 上"原生感不够好"；macOS 27 的 Liquid Glass 又拉开了一代差距 | 每次打开都觉得这是个"外来软件" |

### 1.3 不解决会怎样

- **对用户**：继续用 Navicat（忍受笨重）或退回命令行（忍受低效），一天被这套摩擦吃掉 15-30 分钟
- **对本产品**：如果只是"Navicat 的免费平替"，没有任何理由让人从已有习惯迁过来。**必须有一个明确的、Navicat 给不了的理由**

### 1.4 我们的差异化假设（需要在开发中验证）

> **Navicat 是"功能最全的数据库工作台"，DB Studio 是"反应最快的数据库查看器"。**

具体落到一句话：**从双击图标到看到第一行数据 ≤ 3 秒；任何一个操作都不能让用户等超过 1 秒才看到反馈。**

这不是营销话术，是硬性的工程约束，见 §7 性能预算。如果这个假设不成立（比如 Electron 在 M5 上就是快不起来），整个产品的立基点就没了，需要立刻重新定位。

## 二、目标与成功标准

### 2.1 目标（Outcomes，不是 Outputs）

| # | 目标 | 衡量方式 | 目标值 | 当前基线 |
|---|---|---|---|---|
| G1 | **打开即达**：从冷启动到看到目标表数据足够快 | 冷启动 → 首屏可交互 → 表数据首行渲染，三段耗时 | 冷启动 ≤1.5s；连接恢复 ≤1.0s；表首屏 ≤1.0s；**端到端 ≤3.0s** | Navicat 冷启动约 5-8s（待实测） |
| G2 | **大表不卡**：千万行表可流畅浏览与定位 | 1000 万行表，滚动 + 排序 + 筛选的帧率与响应 | 滚动稳定 ≥ 55 FPS；排序/筛选 ≤1.5s 返回 | Navicat 分页翻页偏慢；DBeaver 全量加载卡顿 |
| G3 | **改数据安全可控**：用户敢在生产库用 GUI 改数据 | 改动是否可预演、可追溯、可撤销 | 100% 写操作有 SQL 预览；100% 危险操作有二次确认 | Navicat 反馈不明确，用户不敢用 |
| G4 | **键盘可达**：高频操作不依赖鼠标 | 覆盖 20 个高频操作的快捷键 | 20/20 有快捷键，且符合 macOS 习惯（用 Cmd 不用 Ctrl） | Navicat 快捷键少且多用 Ctrl |
| G5 | **原生观感**：在 macOS 27 上不违和 | 主观评估 + 对照截图 | 侧边栏/工具栏与 Finder/设置 观感一致 | Navicat 跨平台自绘，原生感不足 |

### 2.2 北极星指标（单机自用也该有指标）

> **北极星：单日完成"连接 → 定位表 → 查/改数据"闭环的次数（Successful Task Completions / Day）**

理由：这是唯一同时反映"快不快"和"好不好用"的指标。如果产品慢，用户会切走去用命令行，这个数就掉；如果不好用，用户会卡在某个环节，这个数也掉。

**驱动指标（L1）**：
- 冷启动耗时 P50 / P95
- 表首屏渲染耗时 P50 / P95
- 会话内操作失败率（执行报错 / 编辑冲突 / 超时中断）
- 日均活跃连接数、日均执行查询数
- 快捷键触发占全部操作的比例（反映 G4 是否真的被用起来）

**健康指标（L2）**：
- 常驻内存占用（目标 ≤ 250MB，Electron 基线约 150MB）
- 网格滚动帧率 P50
- 崩溃次数 / 未捕获异常数
- 单次查询最大结果集行数分布

**采集方式（重要）**：这是单机自用工具，**默认不采集任何数据**。建议做成设置里的"使用统计"开关，默认关闭，开启后数据只写本地 `~/Library/Application Support/DB Studio/telemetry.log`，用于自己看。不做任何网络上报。

## 三、非目标（Non-Goals）

| 不做 | 原因 |
|---|---|
| **数据同步 / 结构同步 / 数据传输** | 这是 Navicat 的护城河，也是它最重、最容易出 bug 的部分（v0.1 已排除）。生产级同步应该用 `mysqldump`/`pg_dump` 或专业 ETL，GUI 做这个反而危险 |
| **ER 关系图** | 投入产出比低。真要建模用 Navicat Data Modeler 或 SQLDBM。（v0.1 已排除，建议永久不做） |
| **定时任务 / 自动化调度** | 需要常驻后台进程 + 调度引擎 + 失败重试，复杂度远超主线收益 |
| **用户权限管理 / 服务器监控** | 目标用户不是 DBA。这是 DBA 工具的能力边界，不是开发者的 |
| **BI / 图表仪表盘** | 数据分析场景，与"间歇性查看修改"的核心场景距离太远 |
| **团队协作 / 云同步 / 账号体系** | 违反"单机自用"定位，会引入整个后端与合规负担 |
| **存储过程调试器 / 报表生成器** | 使用率极低的专业能力，Navicat 有但我们不必对齐 |
| **Windows / Linux 版本** | 聚焦。跨平台会把视觉规范的精力全部吃掉 |
| **多语言** | 只做简体中文 |

> **原则**：凡是 Navicat 有、但会让产品变重或偏离"快"这个立基点的，一律不追。**我们不追求功能数量对等，追求核心链路的体验代差。**

## 四、用户故事

### 4.1 P0：不做就不可用

**连接与导航**
- 作为开发者，我希望双击连接能立刻连上并看到库表树，以便不用每次都输密码和等连接
- 作为开发者，我希望给连接打颜色标签（生产=红），以便在改数据前一眼知道自己在哪儿
- 作为开发者，我希望用搜索框直接搜表名跳过去，以便在几百张表的库里不用手动翻树
- 作为开发者，我希望 SSH 隧道配置能保存并复用，以便连接内网数据库不用每次重填

**查看数据**
- 作为开发者，我希望打开表后能立刻看到前若干行，以便不写 SQL 就能看数据
- 作为开发者，我希望在网格里排序和筛选，以便快速定位到目标行，而不用手写 WHERE
- 作为开发者，我希望长文本 / JSON / 二进制字段能展开看，以便不用导出再打开别的软件

**编辑数据**
- 作为开发者，我希望改完单元格能先看到将要执行的 SQL 再确认提交，以便我知道自己在干什么
- 作为开发者，我希望看到哪些单元格被我改过（高亮），以便提交前能复核
- 作为开发者，我希望执行 DELETE/UPDATE 时如果没有 WHERE 条件会被拦下来，以便不会误删全表

**写 SQL**
- 作为开发者，我希望选中一段 SQL 只执行这一段，以便在一个编辑器里调试多条语句
- 作为开发者，我希望编辑器能补全表名和字段名，以便不用记住所有字段名
- 作为开发者，我希望长查询可以中途取消，以便跑错了不用等它跑完
- 作为开发者，我希望看到执行计划和耗时，以便知道这条 SQL 慢在哪

**导出**
- 作为开发者，我希望把查询结果导出成 Excel 发给同事，以便不用手动复制粘贴
- 作为开发者，我希望导出过程有进度且不卡界面，以便导大表时不用干等

### 4.2 P1：显著提升体验

- 作为开发者，我希望连接断开后能自动重连，以便网络波动不用手动重连
- 作为开发者，我希望查询历史能搜到上周跑过的那条 SQL，以便不用重写
- 作为开发者，我希望常用 SQL 片段能收藏复用，以便少敲重复代码
- 作为开发者，我希望网格能一次选中多行批量删除/导出，以便处理批量数据
- 作为开发者，我希望表结构变更（加字段/改类型）能可视化操作并预览 DDL，以便不手写 ALTER
- 作为开发者，我希望 `.sql` 文件能直接拖进来执行，以便不用复制粘贴
- 作为开发者，我希望外键字段显示关联表的可读值，以便不用手动 JOIN 才知道这行是谁
- 作为开发者，我希望 SQL 一键格式化，以便看别人写的烂 SQL 时不用人肉整理

### 4.3 P2：未来考虑

- 作为开发者，我希望有命令面板（Cmd+K）全局搜索表和执行命令，以便完全不用鼠标
- 作为开发者，我希望 Excel/CSV 能导入到已有表，以便运营给的数据不用写脚本转 SQL
- 作为开发者，我希望查询结果能固定住（pinned），以便对比多次查询结果
- 作为开发者，我希望有本地 SQLite 支持，以便看移动端/桌面端本地数据库

## 五、对标 Navicat 的取舍（Competitive Position）

### 5.1 Navicat 真实的优势（必须承认）

| 优势 | 说明 | 我们的态度 |
|---|---|---|
| **数据/结构同步** | 业界最强，跨库迁移、结构对比同步 | **不追**，明确非目标 |
| **导入导出格式丰富度** | Excel/Access/DBF/XML/JSON/CSV/ODBC 全覆盖 | **部分对齐**：做 Excel/CSV/JSON/SQL 四类即可覆盖 95% 场景 |
| **ER 建模** | 支持关系型/维度型/Data Vault 三种建模法 | **不追** |
| **BI 与图表** | 交互式仪表盘 | **不追** |
| **跨数据库广度** | MySQL/MariaDB/MongoDB/Oracle/SQLite/PG/SQL Server/Redis/Snowflake | **部分对齐**：我们做 MySQL/PG/Redis/MongoDB 四种，够用 |
| **AI 助手**（17.x 新增） | SQL 解释/优化/格式化/纠错 | **观察**：v1 不做，见 Q14 |

### 5.2 Navicat 真实的短板（我们的机会）

| 短板 | 证据 | 我们的机会 |
|---|---|---|
| **资源占用重、启动慢** | 多篇评测提到 "one of the most resource-intensive tools"；安装包 393MB | 冷启动 ≤1.5s，常驻 ≤250MB |

### 5.3 三层取舍结论

**第一层：必须对齐（Navicat 有，用户已形成肌肉记忆，没有会觉得"不完整"）**

连接管理（直连/SSH/SSL）· 分组与颜色标签 · 库表树 · 数据网格（排序/筛选/编辑）· SQL 编辑器（补全/选中执行/历史）· 表设计器（字段/索引/外键/DDL）· 导入导出（Excel/CSV/JSON/SQL）· 执行计划可视化 · 深色模式

**第二层：必须超越（我们的立基点，Navicat 做不到或做得不好）**

1. **速度**——冷启动、表首屏、网格滚动三项全面领先
2. **写操作可预演**——任何改动先给用户看 SQL 再执行
3. **键盘优先**——全 Cmd 键位 + 命令面板
4. **macOS 27 原生观感**——Liquid Glass 侧边栏与工具栏
5. **编辑安全**——脏单元格可视化 + 冲突检测 + 危险操作拦截

**第三层：明确不追**

数据同步 · 结构同步 · ER 图 · BI 图表 · 定时任务 · 权限管理 · 服务器监控 · 存储过程调试 · 报表生成 · 云协作

## 六、功能详述（细化到可实现）

> 凡涉及需求的描述，采用 EARS 风格表述（Ubiquitous / Event-driven / Unwanted / State-driven）。

### 6.1 连接管理

#### 6.1.1 连接配置

| 字段 | 必填 | 说明 |
|---|---|---|
| 连接名 | 是 | 显示名，不与真实库名绑定 |
| 数据库类型 | 是 | MySQL / PostgreSQL / Redis / MongoDB（v1 仅 MySQL 可用，其余置灰显示"即将支持"） |
| 主机 / 端口 | 是 | 端口按类型带默认值（3306 / 5432 / 6379 / 27017） |
| 用户名 / 密码 | 是 | 密码存钥匙串 |
| 默认数据库 | 否 | 留空则连接后展示全部库 |
| 分组 | 否 | 支持"开发/测试/生产"，可嵌套 |
| 颜色标签 | 否 | 8 色可选，生产建议红色 |
| 备注 | 否 | |

**行为要求**
- 系统应始终在保存前提供「测试连接」按钮，返回**耗时（ms）+ 服务端版本 + 错误详情**
- 测试失败时，系统应展示**原始错误码与错误信息原文**，不做翻译或包装（便于自查）
- 密码字段在 UI 上默认遮蔽，提供显示切换；**密码只写入 macOS 钥匙串，配置文件只存非敏感信息**
- 钥匙串读取失败时，系统应提示"钥匙串不可用"并允许用户临时输入密码（不落盘），而不是静默失败

#### 6.1.2 SSH 隧道

- 支持密码认证与私钥认证（私钥文件选择 + passphrase）
- 支持跳板机（SSH 主机/端口/用户 + 目标库主机/端口）
- 私钥文件权限过宽（如 0644）时，系统应**警告**并给出修复命令（`chmod 600`），不静默使用
- 隧道建立应有超时（默认 10s），超时后明确提示"SSH 隧道建立超时"
- 连接关闭时，系统应确保隧道一并释放，不残留孤儿进程

#### 6.1.3 SSL/TLS

- 支持 CA 证书 / 客户端证书 / 客户端密钥三件套
- 提供"不校验证书"开关，开启时在系统内明确标注**不安全**（黄色警示条）
- 证书文件不存在或格式错误时，应在**保存前**校验并提示

#### 6.1.4 连接生命周期状态机

```
空闲 ──点击/双击──> 连接中 ──成功──> 已连接 ──> 空闲忙碌
                      │                  │
                      │失败              │网络中断
                      ▼                  ▼
                   失败(展示错误)      断线(自动重连 x N)
                                          │
                                    重试耗尽 ──> 失败
```

- **空闲忙碌**：连接建立后自动进入，执行查询时保持忙碌，无查询超过 `idleTimeout`（默认 10 分钟）自动断开释放资源
- **自动重连**：网络中断时自动重试，**最多 3 次，间隔 1s/2s/4s**，全部失败后进入失败态并提示
- **重连成功**：系统应恢复用户离开前的树展开状态，并提示"已重新连接"
- 用户在失败态点击「重试」应可手动恢复

#### 6.1.5 首次打开行为（细节）— 已按 D1 拍板

- 双击连接 → 若处于空闲态，先建立连接（展示"连接中"骨架屏，而非阻塞式 modal）→ 成功后展开库表树
- 树展开采用**懒加载**：先渲染库节点，展开库时才查表列表
- 若库数量 > 200，系统应在库节点层提供过滤输入框

**默认展开层级（D1 决策）**：
- 首次连接某连接时，**只展开到数据库层**，不自动展开表列表
- 系统应**持久化记录用户手动展开过的节点**（按 `连接ID + 库名 + 对象类型` 记键），下次打开该连接时自动恢复
- 恢复应异步进行：先渲染库节点，再逐步展开记忆中的节点，**不阻塞首屏**
- 提供设置项「记住展开状态」开关（默认开），以及「清除展开记忆」入口

**实现方式（R11 补充）**：树首屏 ≤500ms 依赖 **schema 磁盘快照**——连接成功后异步拉取一次元数据，落盘到 `userData/schema-cache/<connId>.json`（带版本号与 TTL，建议 7 天）；下次打开**先渲染快照再后台刷新**。快照过期时显示"元数据可能过期"并提供刷新入口。

**验收**：首次打开 100 库的实例，树首屏 ≤ 500ms 完成渲染；二次打开应恢复上次展开的 3 个库节点。

#### 6.1.6 只读模式（D6 决策）

- 连接配置新增「只读模式」开关（默认关）
- 开启后：
  - 网格单元格**不可进入编辑态**；新增行 / 删除行入口置灰
  - SQL 编辑器仍可用（SELECT 正常），但执行到写语句时**在执行前拦截**并提示"该连接为只读模式"
  - 表设计器以**只读**打开，保存按钮置灰
  - 导入功能入口置灰（导入本质是写）
  - 导出功能**保持可用**（只读不影响导出）
- 工具栏/标签页应有**明确的只读标识**（如标签名后灰色锁形标记 + 网格顶部黄色提示条）
- 提供全局快捷键快速切换当前连接只读状态（建议 `Cmd+Shift+L`）

**拦截实现方式（R2 修订，强制）**：不要只靠 UI 置灰（易被绕过），也不要用正则扫关键字（必然漏判）。在主进程执行前做 **SQL AST 语句类型校验**：

1. 用 SQL 解析器（`node-sql-parser`，MySQL / PostgreSQL 方言）解析出 AST，读取语句类型
2. 采用**白名单**而非黑名单，仅放行：
   `SELECT` / `SHOW` / `DESCRIBE` / `DESC` / `EXPLAIN` / `USE` / `SET`（仅安全变量白名单，如 `SET NAMES`、`SET SESSION time_zone`）
3. **多语句**：先按分号拆分，**逐条**解析；任何一条不在白名单则整批拒绝
4. **解析失败 → 拒绝执行**（fail-closed），提示"无法判定该语句是否为只读，已阻止执行"

> **为什么不能用正则**（原 v0.3 方案的缺陷）：正则会漏判 `CALL proc()`、`SELECT … INTO OUTFILE`、PG 的 `WITH … UPDATE`、`CREATE TEMPORARY TABLE`、`LOAD DATA`，以及多语句中的第二条（`SELECT 1; DROP TABLE t`）。这是安全功能，漏判 = 生产事故。手写"跳过注释与字符串"的词法器等于自己写半个解析器，是隐性大坑。
>
> **纵深防御（可选）**：连接建立后执行 `SET SESSION TRANSACTION READ ONLY`（若服务端版本支持）作为第二道闸。**不得作为唯一防线**，其作用域受 autocommit 与事务边界影响，行为不直观。

**验收**：只读模式下，通过快捷键、右键菜单、粘贴、命令面板任一路径尝试写操作，均被拦截且不产生任何服务端变更。另需通过 §12.4 的 R2 专项用例（`CALL` / `SELECT … INTO OUTFILE` / 多语句第二条 / 解析失败）。

### 6.3 数据网格

这是全产品**最核心、最该打磨**的模块。

#### 6.3.1 加载策略

| 模式 | 行为 | 适用 |
|---|---|---|
| **快速打开** | 默认。`SELECT * FROM t LIMIT 3000` | 双击表 |
| **完整打开** | 加载全部（带进度与取消） | `Shift+双击`，或用户确认 |
| **条件打开** | 带 WHERE / ORDER BY | 从筛选器进入 |

- 系统应在网格底部常驻显示：`已加载 3,000 / 约 12,450,000 行（估算）`，并提供「加载更多」按钮（每次 +3000）
- 行数估算来自 `information_schema.TABLE_ROWS`（InnoDB 为估算值），系统应标注"约"字，不谎报精确值
- 超过 10 万行时，系统在打开前提示："该表较大，建议先筛选。仍要打开？"

#### 6.3.2 虚拟滚动

- 仅渲染可视区域 + 上下各 10 行缓冲区
- 行高固定（默认 28px），支持"紧凑 24px / 标准 28px / 宽松 32px"三档
- 滚动目标：**60 FPS**；性能预算见 §7
- 滚动时列头保持吸顶，主键列可选吸左

> **待确认 Q3**（🟡 非阻塞）：是否需要吸左列（冻结列）？建议需要，见 §11。

#### 6.3.3 排序与筛选

**排序**
- 点击列头：无 → ASC → DESC → 无（三态循环）
- 支持多列排序：`Shift+点击` 追加排序列，列头显示序号 ①②③
- 排序在服务端执行（生成 ORDER BY 重新查询），不是前端排序
- 排序按钮旁应有"排序图标 + 序号角标"，让用户知道当前排序状态

**筛选（Filter Builder）**

提供图形化条件构建器，生成的 WHERE 条件**实时可见可编辑**：

```
[字段名 ▾] [操作符 ▾] [值输入框]        [+ 添加条件] [应用] [清空]
条件预览：WHERE status = 'paid' AND created_at > '2026-01-01'
```

- 操作符：等于 / 不等于 / 包含 / 不包含 / 大于 / 大于等于 / 小于 / 小于等于 / 介于 / 为空 / 不为空 / 以…开头 / 以…结尾 / 正则
- 操作符列表**按字段类型动态变化**（数值字段不给"包含"，枚举字段给下拉多选）
- 条件组合：AND / OR，支持一层括号分组（P1）
- 应用后筛选条常驻显示当前条件，点击可再次编辑

> Navicat 已知缺陷："Unable to show long conditions and add new conditions in Filter" —— 我们的条件预览区必须可滚动、可换行、可直接编辑文本

**快捷筛选**
- 列头悬浮出现漏斗图标，点击弹出该列的常用条件（等于/包含/为空）
- 单元格右键「按此值筛选」：`WHERE col = '当前值'`

#### 6.3.4 单元格编辑（核心差异化）

**状态流转**

```
只读展示 ──双击/Cmd+Enter/直接输入──> 编辑中
                                        │
                        ┌───────────────┼───────────────┐
                        ▼               ▼               ▼
                   Esc 取消        回车/Tab 确认     失焦确认
                        │               │               │
                        ▼               ▼               ▼
                     原值恢复        脏单元格(高亮)   脏单元格(高亮)
                                        │
                                   Cmd+S 保存
                                        │
                                        ▼
                              ┌──── SQL 预演弹窗 ────┐
                              │ UPDATE `order`       │
                              │ SET `status`='paid'  │
                              │ WHERE `id`=1024;     │
                              │ [查看全部 3 处改动]   │
                              │ [取消] [确认执行]     │
                              └──────────┬───────────┘
                                         ▼
                              执行 → 成功/失败 → 清除脏标记
```

**硬要求**
- 系统应始终在提交前展示**将要执行的完整 SQL**，多条改动可展开逐条查看
- 改动单元格使用**明确的视觉标记**：左侧色条 + 单元格背景色 + 原值删除线/新值对比
- `Esc` 撤销单个单元格改动；`Cmd+Shift+Z` 撤销本轮全部未保存改动
- 未保存改动时切换标签/关闭表，系统应**拦截并提示**，不允许静默丢失
- 系统应提供"自动保存"开关（默认**关闭**）。开启后每次单元格确认即提交（不弹预演），仅建议在个人开发库使用
- **保存失败**（如唯一键冲突、字段超长）应精确定位到失败行，展示服务端原始错误

> Navicat 17.1.3 曾有"把整行置 NULL 而非仅改选中单元格"的严重 bug —— 我们**必须**做到：只提交被编辑的单元格，绝不整行覆盖。这是验收红线。

#### 6.3.4.1 行定位策略（R4 新增，红线的技术前提）

「只提交被编辑单元格」的**前提是能唯一定位到那一行**。系统应在打开表时判定定位策略：

| 表具备 | 定位策略 | WHERE 构造 | 可否编辑 |
|---|---|---|---|
| 单列主键 | `pk` | `WHERE pk = ?` | ✅ |
| 非空唯一键 | `unique` | `WHERE uk1 = ? AND uk2 = ?` | ✅ |
| 复合唯一但含可空列 | `unique` | 同上，含 NULL 的列改 `IS NULL` | ✅，提示"可空唯一键，存在歧义风险" |
| **无任何主键/唯一键** | `none` | —— | ❌ **网格只读** |

- 系统应在无唯一键的表上，网格顶部展示提示条："该表无主键/唯一键，无法安全定位行，请使用 SQL 编辑"，并禁用单元格编辑态、新增行、删除行、粘贴
- 导出、排序、筛选、查看**不受影响**（只读能力始终可用）
- 外键下拉、JSON 弹窗等查看类交互仍可用

> Navicat 在这类表上的行为正是历史上事故来源之一。**没有唯一键就不允许网格编辑**，这是唯一能保证红线的方式，也让红线在工程上可验收。

#### 6.3.4.2 冲突检测与批量提交语义（R4/R5 新增）

**冲突检测**：生成的 UPDATE 应带上被编辑列的原值，用于识别并发修改：

```sql
UPDATE `order` SET `status` = ? WHERE `id` = ? AND `status` = ?;
```

- `affectedRows === 1` → 成功
- `affectedRows === 0` → 行已被删除或该列已被他人修改 → **标记冲突**，保留改动，提示用户刷新后重新编辑
- `affectedRows > 1` → 立即中止并回滚整批（说明定位条件不唯一，属缺陷，绝不能继续）
- **排除列**：`FLOAT / DOUBLE / JSON / BLOB / GEOMETRY` 的原值不进 WHERE（浮点与二进制比较不可靠），这些列只用主键定位

**批量提交语义（R5 澄清）**：
- 一轮保存（`Cmd+S`）内的所有改动 → **单事务**提交；任一失败则**整轮回滚**
- 回滚后 UI **保留全部脏标记**（不清除），提示："已回滚，共 N 处改动未生效，第 X 行 Y 列失败：<服务端原始错误>"
- 用户修完失败处后可整体再次提交 —— 这是"不丢失用户劳动"的正确解法
- 新增行先 INSERT 拿回 `insertId` 作为该行 rowId；不支持"改一半新行 + 改一半旧行"混在一轮里的部分成功，顺序执行、失败即停

#### 6.3.4.3 驱动连接参数规范（R10 新增）

以下参数直接影响数据正确性，系统应固定配置，不允许默认值：

| 参数 | 值 | 原因 |
|---|---|---|
| `supportBigNumbers` | `true` | 启用大数处理 |
| `bigNumberStrings` | `true` | **BIGINT 一律返回字符串**，避免 >2^53 精度丢失 |
| `decimalNumbers` | `false` | DECIMAL 保持字符串 |
| `dateStrings` | `true` | 保留服务端原文（含 `DATETIME(6)` 微秒），避免"看的是 UTC、写回去变本地时间" |
| `timezone` | `'local'` | |
| `jsonStrings` | `true` | 保留 JSON 原文，避免驱动自动 parse 导致大整数损精度与格式丢失 |
| `multipleStatements` | `false` | 默认禁多语句；`.sql` 脚本导入走单独开关的专用连接 |
| `rowsAsArray` | `true` | 大结果集用数组而非对象，省内存与 GC（网格/导出路径） |

**验收**：见 §12.4 的 BIGINT / `DATETIME(6)` / JSON 大整数三项用例。

**特殊字段编辑**

| 类型 | 展示 | 编辑方式 |
|---|---|---|
| 外键 | 显示关联表可读值（如 `用户：张三`）| 下拉搜索选择 |
| ENUM / SET | 徽章 | 下拉单选 / 多选 |
| JSON | `{…}` 折叠徽章 + 字符数 | 点击弹窗，格式化树 + 语法校验 + 原始/格式化切换 |

| 二进制 | `(二进制 48 B)` | 十六进制预览 + 导出为文件 |
| 日期时间 | `2026-09-20 15:04:05` | 日期时间选择器 + 手动输入，支持 `NULL` 与 `NOW()` |

#### 6.3.6 网格与 Excel 互通（D2 决策：支持粘贴）

**复制**
- 选中区域 `Cmd+C`，默认 TSV 格式（可直接粘进 Excel/Numbers）
- 复制为：`Cmd+Shift+C` 弹出菜单（TSV / CSV / JSON / INSERT 语句 / UPDATE 语句）

**粘贴（v1 范围，已拍板）**
- 从 Excel / Numbers 复制的区域可直接 `Cmd+V` 粘贴到网格
- 粘贴流程：
  1. 解析剪贴板数据（优先 TSV，兼容 HTML table 格式）
  2. **按列对齐**：从当前选中单元格起，按当前列顺序逐列填入。若粘贴列数超过剩余列数，**超出部分丢弃并提示**（不自动新增列）
  3. 行数超出当前末尾时，**自动追加新行**（受行数上限保护，默认单次 ≤ 1000 行）
  4. 逐格做**类型校验**：日期格式不合法 / 数值字段塞字符串 / 超长 / NOT NULL 字段为空 → 该格标红并给出原因
  5. 校验通过的格子标记为**脏单元格**，走统一保存预演流程（§6.3.4）
- 粘贴**不自动提交**，必须显式 `Cmd+S` 并经 SQL 预演
- 提供粘贴预览浮层：显示"将写入 N 行 × M 列，其中 K 处类型不匹配"

**硬要求**
- 粘贴过程中界面不阻塞（>500 行时走 Worker 解析 + 分批渲染）
- 粘贴失败或被取消时，**不得留下部分写入状态**
- 只读模式下粘贴入口不可用（§6.1.6）

**验收**：从 Numbers 复制 200 行 × 8 列粘贴到 1000 万行表，从按下 `Cmd+V` 到脏标记渲染完成 ≤ 800ms；类型不匹配单元格 100% 被标出。

### 6.4 SQL 编辑器

#### 6.4.1 编辑能力

- CodeMirror 6，MySQL 方言
- **自动补全**：关键字 / 数据库名 / 表名 / 字段名 / 别名 / 函数名。补全元数据来自连接时与按需拉取的 schema 缓存
- 补全触发：输入时自动触发 + `Esc` 手动触发
- **选中执行**：有选中执行选中，无选中执行光标所在语句（以分号界定），无分号则执行全部
- 多条语句按分号拆解，逐条执行，结果分 Tab 展示
- `Cmd+/` 注释/取消注释
- `Cmd+Shift+F` 格式化（sql-formatter，可配置关键字大小写、缩进）
- 撤销/重做、多光标、括号匹配、括号自动闭合、引号自动闭合

#### 6.4.2 执行与结果

- `Cmd+R` 执行 | `Cmd+Shift+R` 执行选中 | `Cmd+.` 取消执行
- **执行期间界面不得假死**：编辑器与网格均可继续操作，状态栏显示执行中 spinner + 已耗时
- 结果区：数据网格（复用 §6.3 能力）+ 消息面板（影响行数 / 耗时 / 警告）
- 多结果集：以 Tab 切换，Tab 上显示行数
- **执行超时**：默认 30s，超时后提示"查询仍在运行，是否继续等待 / 取消"（不自动 kill）
- 查询耗时在结果区常驻显示，超过 1s 标黄，超过 5s 标红

**取消与超时的实现路径（R6 新增）**

MySQL 协议**没有带内取消**：查询发出后同一条连接必须等它返回，无法中断。系统应按以下方式实现：

- **取消**：每个连接额外维护一条**管理连接**。用户取消时，用管理连接执行 `KILL QUERY <原连接的 connection_id>`；原连接的查询以 error 返回，前端按"已取消"处理
- **超时提示**：到 30s 时**不 KILL**（慢查询可能是有意跑的），只弹提示；用户选择"继续等待"或"取消"
- **兜底**：连接选项设置 `SET SESSION max_execution_time=<ms>`（MySQL 5.7.4+，毫秒，仅对 SELECT 生效）作为硬上限，防止忘记取消的连接长期占用资源。**需在目标 MySQL 版本上验证可用性**再默认开启，否则降级为纯前端计时
- **流式结果**：导出与大结果集必须用流式 API 边收边写，禁止一次性缓冲到内存

**验收**：取消后需在服务端确认该查询确实被终止（`SHOW PROCESSLIST` 验证），见 §12.4。

#### 6.4.3 EXPLAIN

- 编辑器工具栏「执行计划」按钮，对当前语句执行 `EXPLAIN`
- 表格展示：id / select_type / table / type / possible_keys / key / key_len / ref / rows / filtered / Extra
- **关键列高亮**：`type` 为 `ALL`（全表扫）标红，`Extra` 含 `Using filesort` / `Using temporary` 标黄
- 提供 `EXPLAIN ANALYZE` 切换（MySQL 8.0.18+）
- 支持格式化 JSON 执行计划（MySQL 8.0 的 `FORMAT=JSON`）

#### 6.4.4 历史与片段

- **历史**：每次执行记录（SQL 全文 / 执行时间 / 耗时 / 成功失败 / 影响行数 / 所属连接），存本地 SQLite
- 历史面板支持搜索、按时间倒序、双击回填、右键复制
- 历史保留上限可配置（默认 5000 条），超出自动清理最旧的
- **片段收藏**：常用 SQL 命名保存，支持分类，双击插入编辑器
- 片段与历史应支持导出为 JSON（便于迁移）

| 步骤 | 内容 |
|---|---|
| **1. 选文件** | 支持 `.xlsx` / `.csv`；CSV 可配分隔符、编码、是否含表头、引号规则；多 Sheet 工作簿需选择 Sheet |

**行为要求**
- **事务策略**：提供「单事务（失败全回滚）」与「分批提交（失败跳过）」两种，默认**分批提交**并在结束时给出错误行报告

- 大文件（>10 万行）导入前提示预估耗时
- 导入在 **Worker** 中解析，主线程不阻塞
- 只读模式下入口置灰
- 导入期间允许最小化窗口后台执行，完成后发系统通知

**不在 v1 范围**：UPSERT、导入时自动建表、跨库导入、字段转换函数（如日期格式化）

**验收**：导入 5 万行 × 12 列 CSV 到目标表，总耗时 ≤ 60s，峰值内存 ≤ 600MB；错误行报告 100% 覆盖失败行且可定位。

## 七、性能预算（硬约束）

基于 **M5 Pro (15核/48GB) + macOS 27 + ProMotion 120Hz** 设定。这些是验收门槛，不是愿望。

| 指标 | 目标 | 测试方法 |
|---|---|---|
| 冷启动（进程启动 → 主窗口可交互） | **≤ 1500ms** | 连续 5 次取 P50 |
| 连接恢复（已保存连接 → 树可展开） | **≤ 1000ms** | 本地 MySQL |
| 表首屏（双击表 → 首行渲染） | **≤ 1000ms** | 1000 万行表，LIMIT 3000 |
| 网格滚动帧率 | **≥ 55 FPS**（120Hz 屏目标 ≥ 100 FPS） | 滚动 10000 行采样 |
| 排序 / 筛选响应 | **≤ 1500ms** | 1000 万行表带索引字段 |
| SQL 执行结果首行渲染 | **≤ 500ms**（不含查询本身） | 1 万行结果集 |
| SQL 编辑器首字符输入延迟 | **≤ 16ms** | |
| 自动补全是延迟 | **≤ 100ms** | |
| 常驻内存（**空闲 5 分钟后**，1 个连接 5 个标签） | **≤ 250MB**（R8 口径修订） | 活动监视器 |
| 导出 100 万行到 xlsx | **≤ 30s**（S3 实测 6.26s，保留原预算），峰值内存 **≤ 1.2GB**（S3 修订，原 ≤500MB 不可达） | |
| 窗口缩放 / 切换标签重绘 | **≤ 100ms** | |

> **R7 说明（S3 已实测，2026-09-21）**：`exceljs` 流式 + `useSharedStrings:false` + `useStyles:false`，100 万行 × 12 列实测 **P50 6.26s**（M5 比公开基准 89s 快约 14 倍），**原预算 ≤30s 保留，不退到 ≤60s**。
> **但峰值内存 ≤500MB 不可达**：实测 **987MB**（默认配置更高达 2739MB）。评审预估"流式下 ≤500MB 很轻松"不成立——公开基准的 92MB 是**输出文件体积**，不是进程内存。故重定为 **≤1.2GB**（987MB + 20% 余量）。导出运行在 `utilityProcess` 内，进程结束内存即释放，**不影响常驻内存 ≤250MB 指标**。
> **实现选型：采用 exceljs 流式（E3），不采用手写 sheet XML（E4）**。E4 虽快 2 倍（3.12s），但**日期会退化为裸数字**（写 Excel 序列号却无 `numFmt` 样式，读回变 `43831.0000115741`）——"失去样式能力"的真实代价是**数据类型损坏**，不只是观感。E4 仅作为未来 >300 万行导出的备选，届时须同时实现 `styles.xml`。
> 详见 `docs/engineering/SPIKE-REPORT-v1.0.md` §四。
>
> **R8 说明**：Electron 空壳基线已约 150MB，只剩 100MB 给应用。刚跑完一个 10 万行查询时略超是合理的，故明确为「空闲 5 分钟后」。配套措施：结果集列式存储、后台标签数据淘汰（切走的标签只保留 schema + 前 100 行预览）、导出在独立进程结束后内存即释放。

### 7.1 关键工程措施

- **Electron 版本：≥ 42，锁定 44.x**（R1 修订）。三条约束取高者：
  - **下限 38.2.0**（或 36.9.2 / 37.6.0 修复线）：低于此版本在 macOS 26+ 存在 WindowServer GPU 空转 bug（Electron 滥用私有 `_cornerMask` API，导致 WindowServer 反复重绘阴影），会造成**系统级**卡顿
  - **下限 41**：`electron-window-glass` 要求（D4 决策）
  - **下限 42**：41 已于 2026-08-25 EOL，42 于 2026-10-20 EOL。**工程锁定 44.x**（Node 24.18 / Chromium M152 / EOL 2027-03-02），避免一开工就背着 CVE 与支持断供
  - 升级策略：固定"跟随 stable-1"，新版本发布后观察 2 个小版本再升。**不追 alpha/beta**（本项目无 QA 资源）
- **窗口不要启用 `vibrancy`**，改用 `transparent: true` + 原生 `NSGlassEffectView`（见 §8.1）
- 虚拟滚动：只渲染可视区 + 缓冲区，行高固定，禁止在滚动路径上做对象分配
- 数据分片：网格按 3000 行分片，导出按流式写入
- **结果集走列式 `ArrayBuffer` transfer 传输**（R 新增）：主进程编码成列式二进制（数值列 TypedArray + nullMask；字符串列 offset 数组 + UTF-8 拼接）后零拷贝 transfer，渲染侧**只解码可视区**。这是保证「首行渲染 ≤500ms」与渲染端内存有界的前提
  > ⚠️ **论证依据已按 S5 实测更正（2026-09-21）**：原表述称"JSON 会吃掉 300~600ms、且列式能从 15MB 降到 2~4MB"。**在本 PRD 指定规模（LIMIT 3000）下这两点都不成立**：列式体积 0.477MB vs JSON 0.443MB（**列式并不更小**），列式编码 4.15ms vs JSON 0.70ms（**列式反而慢 3~5 倍**）。
  > **列式的真实价值是另外三条**：① **只解可视区**——列式解 40 行恒定 0.029ms 且与结果集大小无关，JSON 必须全量解析（1.10ms @3000 行，**338ms @50 万行**）；② **渲染端内存有界**；③ **大结果集可扩展**。
  > **结论：方案保留，但不要再拿"省体积/省编码时间"当理由。** 若未来有人提议改回 JSON，正确的反驳是"大结果集下 JSON 全量解析会卡死渲染进程"，而不是"JSON 更大"。
- 主线程保护：所有数据库操作在主进程；**导出/导入解析/大 JSON 格式化放 `utilityProcess`**（可 `kill()`，因此"取消"是真取消；崩溃不拖垮主进程），不用 `worker_threads`
- Schema 缓存：连接后异步拉取一次元数据并落盘快照，避免补全时每次查库（见 §6.1.5）

### 7.2 冷启动达标措施

- **驱动懒加载**：`mysql2` / `ssh2` / `pg` 等原生模块在**首次连接时** `await import()`，不在 `app.whenReady()` 里 require
  > ⚠️ **预期已按 S2 实测更正（2026-09-21）**：评审称这是冷启动"最大的一块"、"缺一件基本没戏"。**实测不成立**——三个驱动 + `node:sqlite` **全部同步加载只花 26ms**（mysql2/pg 是纯 JS，ssh2 默认走 JS 实现，M5 解析极快）。
  > **真正的固定成本是 Electron 运行时初始化 63ms + 渲染进程启动 ~107ms（合计约 170ms，占打包版 217ms 的 78%），懒加载动不了。**
  > **因此冷启动的真实风险不在驱动，而在应用首屏 JS 体积。** 懒加载仍照做（成本极低、对未来依赖膨胀是保险），但**不要指望它救冷启动**。配套约束见 §12.2 的子预算与「首屏 bundle ≤1.5MB 未压缩」。
- **CodeMirror 懒加载**：首次打开查询标签时才载入
- **历史库延迟打开**：`node:sqlite` 在首屏渲染完成后再开
- **启动路径上禁止任何网络 / DNS / 钥匙串同步调用**：`safeStorage.isAsyncEncryptionAvailable()` 是异步的，不得在同步路径上 await 而挡住窗口创建
- `asar` 开启但 `compression` 用默认而非 `maximum`（最高压缩显著拖慢首次启动）
- **测的是第二次及以后的启动**，首次启动受 Gatekeeper 校验影响，不计入

### 7.3 ✅ 已解除：玻璃与网格帧率的冲突不成立（S1 实测，2026-09-21）

原风险：`transparent: true` 会强制 Chromium **关闭 GPU 合成、退回软件光栅化**，与「网格滚动 ≥55FPS / 120Hz ≥100FPS」直接冲突。

**S1 实测结论：冲突不成立。** 四组对照（透明+玻璃 / 透明无玻璃 / 不透明 / 不透明+100 行上限校验）的 P50 **均为 120.5 FPS、掉帧率 0%**，已贴满 120Hz 上限。透明+玻璃与不透明对照**完全相等**，未产生任何可观测 FPS 惩罚。GPU 设备为 `ANGLE Metal (Apple M5 Pro)`，Canvas / Compositing / Rasterization 均 `Hardware accelerated`。

- **D4 采用方案 A（整窗原生玻璃 + 内容区不透明），已达成，可写进排期承诺**
- 判定表与实测值见 §8.1.1；完整报告见 `docs/engineering/SPIKE-REPORT-v1.0.md` §一
- **保留边界**：探针为最小虚拟滚动网格（每帧约 28 可见行）。真实组件若含图片/富样式单元格，落地前需同法重负载复测，作为验收闸门
- 降级路径（运行时 FPS<50 自动关玻璃）作为跨机型保险**保留**

## 八、视觉与交互规范（macOS 27 适配）

### 8.1 设计语言：Liquid Glass（D4 决策：引入原生方案）

macOS 27 上，Apple 的 Liquid Glass 已是系统级视觉语言。若仍用 `backdrop-filter` 模拟毛玻璃，会明显"差一代"。

**已拍板方案**：`electron-window-glass`，`kind: 'glass'`（原生 `NSGlassEffectView` 公开 API 绑定）

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| **A. `electron-window-glass` kind: 'glass'** | 公开 Liquid Glass API；观感与系统一致；性能好 | 需 macOS 26+ 且 Electron 41+；依赖第三方包 | ✅ **采用** |
| B. `kind: 'backdrop'`（Core Animation 私有符号）| 效果可细调 | 用私有 API，Apple 可随时改；不适合 MAS 分发 | ❌ 不用 |
| C. CSS `backdrop-filter` 模拟 | 零依赖 | 观感差一代；GPU 开销大；与真原生面板并排有"恐怖谷" | ⚠️ **仅作降级** |

**关键配置约束**
- 窗口必须 `transparent: true`，**且不能同时开 `vibrancy`**（会冲突导致模糊错乱）
- `roundedCorners: false` + 由 glass 提供 `cornerRadius`
- 玻璃观感只体现在**浮动导航层**（侧边栏、工具栏、浮层），**内容层不透明**（网格、编辑器、卡片）。这是 Apple 的明确指引
- 多个玻璃元素放进 `NSGlassEffectContainerView` 保证采样一致

**⚠️ 落地形态已修订（R3）**

原 v0.3 设想「侧边栏加玻璃、内容层不加」在当前包上**不可实现**：`electron-window-glass` 只提供**窗口级** API（`createWindowGlass(window, options)`），没有 subview / region 级能力。

实际落地形态为：**整窗附加原生玻璃 + 渲染层内内容区完全不透明**。观感上仍是"chrome 玻璃、内容实体"，符合 Apple 指引。详见 §8.1.1。

**其他工程约束**
- **系统版本判断用 `os.release()`（Darwin 内核主版本 ≥ 26）**，不要解析市场版本号、不要依赖 build 号推断。
  > ⚠️ **S4 实测更正（2026-09-21）**：本机 `os.release()` 返回 **`27.0.0`**（Darwin **27**），而非此前文档所称的 26——原文把 **build 号 `26A428` 误当成了 Darwin 内核版本号**（`sw_vers` 显示 ProductVersion 27.0 / BuildVersion 26A428）。阈值 `>= 26` 仍然安全（27 ≥ 26），玻璃可正常启用，故未造成功能问题；但**判据必须写明**：用 `os.release()` 取内核主版本，**不要假设 Darwin 主版本 = macOS 市场版本减一**（历史映射参考：15→24、26→25、27→27）。阈值集中定义为常量。
- 圆角由 glass 的 `cornerRadius` 提供，**渲染层不自己画窗口级圆角**；内容区四角会被裁切，滚动条与右下角状态栏须留安全边距
- 交通灯：`frame: false` 后需自行实现原生交通灯位置与行为，**具体可用 API 需在 Spike 中实测确认**，不凭文档想当然
- 降级实现必须**同步 try/catch**：包在 macOS < 26 上请求 `kind: 'glass'` 会**抛异常**，`GlassProvider.applyTo()` 必须包住，禁止异常冒泡到 `app.whenReady()`

#### 8.1.1 三种落地形态与决策树（Spike S1 决定）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 整窗玻璃 + 内容区不透明**（优先验证） | 主窗口 `transparent: true` + `backgroundColor:'#00000000'` + `roundedCorners:false` + `createWindowGlass(win,{kind:'glass'})`；渲染层侧边栏/工具栏/浮层用半透明，网格/编辑器/卡片用完全不透明 | 单窗口，无同步问题；观感符合 Apple 指引 | `transparent:true` 可能触发软件光栅化 → **网格 FPS 崩** |
| **B. 主窗不透明 + 玻璃子窗口** | 侧边栏/Inspector/命令面板各开 frameless 透明 `BrowserWindow`（`parent: mainWin`）单独加 glass | 主窗保留 GPU 合成，网格性能不受影响 | 子窗跟随父窗移动/缩放有可感知延迟；焦点与 z-order 管理复杂；多窗口让 `Cmd+W` / `Cmd+\`` 等快捷键语义变复杂 |
| **C. 主窗不透明 + CSS `backdrop-filter`** | 不用原生 glass，侧边栏用 CSS 毛玻璃 | 零 native 依赖、性能最好 | 观感"差一代"，PRD 判定仅作降级 |

**决策树（Spike S1 输出）**

1. 方案 A 下测 10000 行 × 20 列虚拟滚动在 120Hz 的 P50 FPS
2. **P50 ≥ 100** → 采用 A，D4 目标达成
3. **50 ≤ P50 < 100** → 采用 A，玻璃仅用于侧边栏与浮层，并在设置页诊断信息中展示网格滚动 FPS
4. **P50 < 50** → 采用 B（或 C），**D4 降级为"侧边栏 CSS 毛玻璃 + 命令面板/浮层用原生玻璃小窗口"**，并向产品同步：原生玻璃与 120Hz 网格在本机不可兼得

> 补充降级触发条件：运行时检测到网格滚动 FPS < 50 时，允许自动关闭玻璃（在 `GlassProvider` 中实现）。

**判定规则（C2 确认，工程可直接执行，无需再次评审）**

| 实测 P50 FPS | 采用 | 玻璃范围 | D4 是否达成 | 额外动作 |
|---|---|---|---|---|
| ≥ 100 | **A** | 整窗原生玻璃，内容区不透明 | ✅ 达成 | 无 |
| 50 ~ 99 | **A** | 仅侧边栏 + 浮层 | 🟡 部分达成 | 设置页展示网格 FPS 诊断 |
| < 50 | **B**（或 C） | 侧边栏 CSS 毛玻璃 + 浮层用原生玻璃小窗 | ❌ 降级 | 同步产品：原生玻璃与 120Hz 网格不可兼得 |

**S1 实测结论（2026-09-21 由工程填入，S1 已完成）**

| 项 | 值 |
|---|---|
| 实测日期 | **2026-09-21** |
| 透明 + 玻璃 P50 / P95 FPS | **120.5 / 133.3**（掉帧率 0%） |
| 不透明无玻璃（对照）P50 / P95 FPS | **120.5 / 131.6**（掉帧率 0%） |
| **判定采用方案** | **A**（整窗原生玻璃 + 内容区不透明） |
| D4 是否达成 | **✅ 达成** |

> 依据 `spike/s1-glass-grid/RESULTS.md`。四组对照 G1（透明+玻璃）/ G2（透明无玻璃）/ G3（不透明）/ G4（不透明+100 行上限校验）**P50 均为 120.5 FPS、掉帧率 0%**，已贴满 120Hz 上限。
> **B1 冲突不成立**：`transparent: true` 未产生可观测 FPS 惩罚（G1 与 G3 完全相等）。GPU 设备为 `ANGLE Metal (Apple M5 Pro)`，Canvas / Compositing / Rasterization 均 Hardware accelerated。
> **落地要点**：① 玻璃包为 ESM-only，必须 `await import()`，`require` 会抛 `ERR_PACKAGE_PATH_NOT_EXPORTED`；② 交通灯用 `setWindowButtonPosition` + `setWindowButtonVisibility`（`titleBarStyle` 仅 `frame:true` 可用，与玻璃形态冲突）；③ 自带 arm64 预编译产物，**无需 rebuild**。
> **保留边界**：探针为最小虚拟滚动网格（每帧约 28 可见行）。真实组件若含图片/富样式单元格，落地前需同法重负载复测。降级路径（FPS<50 自动关玻璃）作为跨机型保险保留。

**冲突时的优先级（事先约定，避免届时扯皮）**

若 P50 < 50 必须二选一，**优先保网格帧率（G2），放弃原生玻璃**。理由：本产品立基点是"反应最快的数据库查看器"（§1.4），滚动卡顿直接摧毁核心体验；而玻璃是观感增强项，CSS 毛玻璃已能交付 80% 的观感收益。

**降级路径（强制要求）**

必须封装一层 `GlassProvider`，在以下任一情况自动降级到 CSS 毛玻璃，**不允许崩溃或白屏**：
1. macOS < 26（请求 `kind: 'glass'` 会抛异常）
2. 原生模块加载失败（架构不匹配、签名问题、缺失 dylib）
3. 用户在设置中手动关闭"使用原生玻璃效果"

```ts
// 建议接口形态
interface GlassProvider {
  readonly mode: 'native' | 'css' | 'none';
  applyTo(window: BrowserWindow): void;
  dispose(): void;
}
```

应用启动时应在设置页显示当前生效的渲染模式（如"侧边栏：原生玻璃"），便于自查。**建议同时显示"降级原因"**（模块加载失败 / 用户手动关闭 / FPS 保护 / 系统版本不足）。

**工程影响**：Electron 需 **≥ 42，锁定 44.x**。三条约束取高者——38.2.0 修复 macOS 26+ GPU 空转 bug，41 是本包要求，42 是 EOL 现实。**取 42，锁 44.x**。

**成熟度风险**：`electron-window-glass` 目前仅 2 个版本（1.0.0 发布于 2026-08-22），社区验证样本极少。这不构成阻塞（有降级路径），但必须在 Spike S4 中验证其在 Electron 44 + arm64 上可正常运行，且打包后有可用预编译产物。

| 数据 | 存储位置 | 说明 |

| 导出默认目录 | 记住上次选择 | |

- **连接配置应支持文件级导出/导入**（JSON，不含密码），便于换机器迁移 → 建议从"待确认"提升为 v1 必做
- 钥匙串不可用时的降级策略见 §6.1.1

### 10.1 凭据与本地库实现约束（R9 新增）

**凭据**
- 统一使用 `safeStorage` 的**异步 API**（`encryptStringAsync` / `decryptStringAsync`）。原因是 macOS 上访问钥匙串可能弹权限确认并**阻塞当前线程**，同步 API 会卡住主进程
- 启动顺序：`app.whenReady()` 之后先 `await safeStorage.isAsyncEncryptionAvailable()`；不可用则整连接进入"每次手动输密码、不落盘"模式（降级策略见 §6.1.1）
- 私钥 passphrase 同样走 safeStorage

**本地历史库**
- 使用 Node 内置 `node:sqlite` 的 `DatabaseSync`（Node 22.13+ 免 `--experimental-sqlite`，Electron 44 带 Node 24.18 可用）
- **只用核心 API**：`DatabaseSync` / `StatementSync` / `exec` / `prepare` / `run` / `get` / `all` / `iterate`。**不要碰** `createSession` / `applyChangeset` / `createTagStore` 等仍在演进的接口，避免升级 Electron 后 API 漂移
- 必须 `PRAGMA journal_mode=WAL`
- 所有写操作走 prepared statement（防注入 —— 历史库里存的 SQL 全是用户原文）

- [ ] 冷启动 ≤ 1500ms（P50，**取第二次及以后的启动**；S2 实测打包版 217ms）

- [ ] 表首屏 ≤ 1000ms（S5 实测 8.4ms）
- [ ] 网格滚动 ≥ 55 FPS（S1 实测 P50 120.5 FPS，已贴满 120Hz 上限）
- [ ] 常驻内存 ≤ 250MB（**空闲 5 分钟后**）
- [ ] 100 万行导出 xlsx：**≤ 30s**，峰值内存 **≤ 1.2GB**（S3 修订：耗时实测 6.26s，内存实测 987MB，原 500MB 不可达；运行在 utilityProcess 内，不影响常驻 250MB）

### 12.3 红线（任一不满足则不予发布）

1. 编辑保存只提交被编辑的单元格，绝不整行覆盖
2. 任何写操作必须可预览 SQL 原文
3. 生产环境危险操作必须有第三层确认
4. **Electron 版本 ≥ 42（锁定 44.x）**（同时满足 macOS 26+ GPU 空转修复、原生玻璃要求与 EOL 现实）
5. 密码绝不写入本地配置文件
6. 原生玻璃任何失败路径都必须降级，不允许崩溃或白屏
7. **无主键/唯一键的表，网格必须为只读**（红线 1 的技术前提）
8. **只读模式下任何写语句均被拦截**（含 `CALL` / 多语句第二条 / 解析失败场景）

### 12.4 工程验收补充（R12 新增，来自技术评审）

数据与正确性：
- [ ] 无主键/唯一键的表，网格只读并给出明确提示
- [ ] BIGINT 超过 2^53 的值在网格与导出中保持精确（不出现 …000 尾数）

- [ ] JSON 字段中的大整数不被自动 `JSON.parse` 损精度

- [ ] 只读模式下 `CALL` / `SELECT … INTO OUTFILE` / 多语句第二条写操作，全部被拦截
- [ ] 只读模式下解析器报错时，语句被拒绝执行（fail-closed）
- [ ] 编辑保存时，被他人修改过的行被识别为冲突且不覆盖（`affectedRows=0`）
- [ ] 配置文件中不出现任何明文密码（`grep` 验证）

进程与资源：
- [ ] 长查询取消后，服务端该查询确实被终止（`SHOW PROCESSLIST` 验证）
- [ ] 应用退出后无 SSH 隧道孤儿进程
- [ ] 导出中途取消，输出文件不存在或明确标记为未完成（不留半截 xlsx）

打包与启动：
- [ ] 打包产物在 arm64 上能正常启动（含原生模块加载、玻璃降级路径）
- [ ] 冷启动取**第二次及以后**的 P50
