# 0.7.4 / 0.7.5 / 0.8.0 三版研发合并纪要（2026-11-11）

> **为什么合并成一份**：三版的**范围依据是同一份文档**（`product/PLAN-版本迭代任务清单-2026-11-10.md`，2026-11-10 全项目只读审计产出），是同一轮审计后连续三批落地的。逐版单开 REQ 会产生大量重复的「背景/依据」段落，横向对照（哪些是 P0、哪些后来改了主意）反而更难查。
>
> **逐版细节在 `RELEASES.md`**（每版都写了根因、修法、门禁数字、遗留项）。本文只做**横向汇总**：22 项改动一览、6 处证伪验证、遗留清单。

---

## 一、三版定位

| 版本 | 主题 | 一句话 | 选项取舍 |
|---|---|---|---|
| **0.7.4** | 缺陷清零 | 审计出的 **10 个 P0** 全部修掉——都是「界面说成功、实际没成功」或「明明有入口却做不成」 | 只做缺陷 + 让缺陷能被验出来的最小门禁子集，**不掺新功能、不动架构** |
| **0.7.5** | 一致性与上手 | **8 类 P2** 收口——同类东西在不同地方表现不一致、以及新手第一次用会卡住的地方 | 只做低成本、用户可感知的一致性，**不动架构** |
| **0.8.0** | 验收可信度与规模 | 让**门禁真正具备证伪能力** + 补掉几个「看着在工作、实际会静默失败」的隐蔽缺陷 | 唯一新功能是 powerMonitor；主要价值在**测试可信度**而非功能增量 |

**为什么按这个顺序**：审计结论是「**优先修可靠性，再补高频交互；暂不把 PostgreSQL / AI 当作下一轮默认方向**」（`research/竞品调研与功能路线图.md:20-27`）。所以先 P0 缺陷 → 再 P2 一致性 → 最后补验收可信度。P3 红线项（PG/Redis/Mongo、AI、自动更新）**三版都没碰**。

## 二、22 项改动一览

### 0.7.4 · P0 十项（#35–#44）

| # | 问题 | 本质 |
|---|---|---|
| #35 | 冲突整批 ROLLBACK 后历史仍记「成功」 | 把「事务已回滚」写成成功，**历史欺骗用户** |
| #36 | `schemaRefresh` 吞异常致 DDL 假成功 | catch 里什么都不做 → 建库失败也弹「已创建」 |
| #37 | 删表/批量删表回执被「已刷新表结构」覆盖 | `setToast` 在 `await refresh` **之前**调，回执被后到的盖掉 |
| #38 | 空表/0 行无法录入第一行 | 空态占位块盖住网格，没有「新增空白行」入口 |
| #39 | 取消查询无条件报成功 | `await onCancel(id).catch(()=>false)` 后直接 toast「已发送」 |
| #40 | 手输密码后 SQL 已执行但结果丢失 | 返回伪造 `cancelled:true`，真结果 Promise 无人接收 |
| #41 | 字节预算截断被静默 | `openTable` 用行数判据**覆盖**了 `budget.truncated` |
| #42 | `schemaGet` 失败把已握手成功的连接标 failed | 握手与读结构混在一个 try |
| #43 | 五个模态无 Esc 退路 | 违反 AGENTS §八；其中一个（设计器）是**唯一退不出的模态** |
| #44 | 剪贴板失败仍报「已复制」 | 不检查 `navigator.clipboard` 结果 |

## 三、6 处证伪验证（本项目最看重的实践）

**「断言必须在错误实现上确认会红」**——三版共做 6 次，每次都把实现改坏、看报红、再改回。这是防止「恒真假绿」的唯一手段。

| 版本 | 项 | 破坏方式 | 结果 |
|---|---|---|---|
| 0.7.4 | #35 | 退回 `success: true` | 反例断言报红 `expected true to be false` |
| 0.8.0 | #45 | `buildCopyTableSql` 的 withData 短路 | 20/22，「含数据复制」2 条红 |
| 0.8.0 | #47 | 退回 200 行采样 | 「大值在后段」红 |
| 0.8.0 | #46 | `isCurrent` 恒 true | 5 条红 |
| 0.8.0 | #79 | `tryAcquire` 无条件覆盖 | 3 条红（`expected [] to deeply equal ['save']`） |
| 0.8.0 | #51 | 注入 `var(--radius-sm)` | 精确报出变量名 |

## 四、三版抓到的「假绿」类型（方法论沉淀）

审计与落地过程中，门禁/断言失效有 5 种常见形态，已全部转化为机制防线：

| 形态 | 实例 | 防线 |
|---|---|---|
| **恒真断言** | demo 后端 `mutationApply` 恒 `committed:true`，12 个 DDL 入口只断言 SQL 文本 | `e2e:ddl:real` 真库回读（#45） |
| **前提不成立记绿** | `check(..., true)` 把「没跑」算通过 | `skipped` 显式计数，不进通过率（0.7.4） |
| **判据照旧实现写** | 交通灯色度 >35 把灰圆滤掉 → 报「灯不见了」 | 拆「存在性（彩色∪灰）」+「颜色」两段（0.7.4 前移） |
| **采样外推代替真实值** | 前 200 行估平均行宽 → 前窄后宽时预算失效 | 全量真实累计（#47） |
| **反向引用无人查** | `var(--radius-sm)` 未定义，声明静默失效 | 幽灵 token 门禁（#51） |

## 六、如实登记的遗留（三版累计）

**做了但没做完**
- **#47 峰值内存**：驱动仍把全量 rows 读进内存，需 mysql2 流式改造（触碰驱动抽象层）。本版只修了**截断判据**，峰值风险仍在。
- **#78 连接数上限**：与休眠释放同单，但上限值/超限告知方式属产品口径，未定，故未做。
- **#51 覆盖度增强**：`e2e:perf` / `transfer:ui` 纳链有 flaky 风险，未纳入。

**明确没做（非漏项）**
- `⌘C/⌘V/⌘A/⌘Z` 与系统 role 优先级、原生菜单 accelerator、真实 IME 组合期 —— 仍是 `e2e:keys` K7 **人工终验**项。
- 全角加号 `＋`（`TableDesigner` 按钮文案前缀）未换 SVG —— 会改变可见文案、e2e 依赖，留待单独一轮。
- P3 红线项（PG/Redis/Mongo、AI、自动更新）**三版未碰**，仍登记在 `PLAN` 文档 §3。

## 七、三版共同的一条教训

**「门禁报红先问：这个红是我造成的，还是环境造成的」**——三版里出现过 3 次环境假红（锁屏致 CDP 超时、前台非目标窗口致交通灯"消失"、维护命令对坏表返回 Error 行而非抛错）。每次都先排查环境、用全屏截图/独立脚本取证，再下结论，**没有一次把环境问题误报成产品缺陷**。
