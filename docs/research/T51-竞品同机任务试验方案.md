## 0. 为什么这份方案要写这么细

调研报告的判断是「尚未进行同机任务试验」，因此**不能回答「我们是否更快」**（`REQ-0.7.0:929` 待确认问题 #4）。
同机试验最容易出的三类假结论：

1. **拿厂商宣传数字做比值**——TablePro/TablePlus 官网的「快 N 倍」不是同机测量（报告 `:914` 明确禁止）；
2. **口径不同还相减**——一个工具只取前 1000 行、另一个流式全量，比「首次可交互」没有意义；
3. **把噪声当差异**——单轮测一次、差 40ms 就宣布胜负。

所以本文的重点不是「测哪些场景」（那是报告给的），而是**每个场景的准备数据、操作步骤、指标定义、判据**四件事写死，让第二个人照着做能得到同一结论。

## 1. 方法约束（先立规矩，再谈场景）

### 1.1 同机与同条件

| 项 | 要求 | 记录方式 |
|---|---|---|
| 机器 | 全程同一台（建议本机 M5 Pro；**不允许换机重测后合并**） | 型号 / 芯片 / 内存 |
| 系统 | 同一 macOS 版本，同一系统缩放 | `sw_vers`、显示器设置截图 |
| 屏幕 | 同一块屏、同一分辨率与缩放、**外接屏断开**、不镜像 | 系统设置截图 |
| 刷新率 | 固定 120Hz（ProMotion 关闭「自动」） | 系统设置截图 |
| 电源 | 全程接电，关闭低电量模式 | 菜单栏截图 |
| 后台 | 除被测应用与录屏外，关闭其它常驻应用（尤其 Docker Desktop / 浏览器多标签） | `ps` 快照 |
| 数据库 | 同一 fixture 实例（`127.0.0.1:13306`），同一 `innodb_buffer_pool_size` | 启动参数 |
| 窗口 | 每个应用都最大化到同一尺寸（记录实际 px） | 截图 |

### 1.2 冷 / 热

- **冷**：先退出应用，再启动，**首个操作**即为该场景。操作系统页缓存无法真正清空，除非 `sudo purge`（需管理员，且会影响其它进程）——**方案默认不做 `purge`，并在记录表里注明「冷=应用冷启动，非 OS 冷缓存」**。
- **热**：同一张表第二次打开、或在同一会话内重复同一操作。
- 冷热**分开成表**，不混算。首轮一律记为冷，不参与 P50/P95。

### 1.3 多轮与分位数

- 每个场景每个产品 **≥7 轮有效样本**（首轮冷启动单列，不计入）。
- 报告 **P50 / P95**：样本数 n=7 时 P95 取 nearest-rank（第 7 个），**不要用插值**——n 太小时插值会造出不存在的数。
- **判定「有差异」的前提**：差值 > 该指标自身的轮间离散度（用 P95−P50 或极差描述）。差值小于离散度 → 记「不可区分」，不排名。
- 每轮记录原始值，不只记汇总（否则事后无法复核）。

### 1.4 服务器耗时 vs 客户端耗时

- **服务器耗时**：在 fixture 上取 `performance_schema` 前后快照差值，按 `DIGEST_TEXT` 归集。
- **客户端耗时** = 墙钟 − 服务器耗时（**近似值**，含 IPC/渲染/GC，不细分）。
- ⚠️ 不同工具可能改写 SQL（加 `LIMIT`、拆批、加 `SQL_NO_CACHE`…）。所以：
  1. 每轮必须记录工具**实际发出的 SQL 文本**（fixture 侧开 `general_log` 只在该场景开，用完关——它有 I/O 开销，不能全程开）；
  2. 改写导致语句不同时，**服务器耗时不具可比性**，只报各自值，不做比值。

```sql
-- 快照 1（场景开始前）与快照 2（结束后）各跑一次，落临时表
CREATE TEMPORARY TABLE t51_snap AS
SELECT DIGEST_TEXT, COUNT_STAR, SUM_TIMER_WAIT
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME IN ('t51_trial','bench');

-- 场景结束后取差值（SUM_TIMER_WAIT 单位皮秒，/1e9 → 毫秒）
SELECT s.DIGEST_TEXT,
       (e.COUNT_STAR - s.COUNT_STAR)              AS calls,
       (e.SUM_TIMER_WAIT - s.SUM_TIMER_WAIT)/1e9  AS server_ms
FROM t51_snap s
JOIN performance_schema.events_statements_summary_by_digest e USING (DIGEST_TEXT);
```

> 该方法的已知误差：digest 会归一化字面量，慢查询与快查询可能落到同一 digest；`general_log` 本身拖慢写入。两者都要在报告里写明，不能把「服务器耗时」当成精确到毫秒的真值。

### 1.5 120Hz：看长帧与输入延迟，不看平均 FPS

- **长帧**：统一用「录屏中画面连续 ≥2 帧未更新」的比例（60fps 录屏下 ≈ ≥33ms，与报告 `:568` 的 33.4ms 阈值同量级）。**不允许**用「平均 FPS」下结论——平均 FPS 会把 1 次 200ms 卡顿和 200 次 8ms 抖动算成同一件事。
- **输入延迟**：手机 240fps 慢动作同时拍「键盘/触控板」与「屏幕」，从按键首帧到画面首帧变化的帧数 ÷ 240。只对**键盘场景（S10）与定位场景（S1）**做，不做全场景。
- **只有本产品能测的指标**（如 CDP trace、`performance.now` 长任务）**不进入横向对比**，只做本产品的纵向基线。混进去就是「用不同的尺子量两样东西」。

### 1.6 明确禁止

- ❌ 用厂商官网/发布会的性能数字做比值（报告 `:914`、`:568`）；
- ❌ 跨机器比较（「我这边 200ms，他那边 50ms」）；
- ❌ 只测一轮就下结论；
- ❌ 混用不同的 `fsync` / 事务设置（`innodb_flush_log_at_trx_commit`、`sync_binlog`、工具自身的批量事务）；
- ❌ 把「首次可交互」与「全部加载完成」混为同一指标；
- ❌ 在报告里只写结论不写口径。

## 3. 十个场景

> 每个场景固定四段：**准备数据 → 操作步骤 → 记录指标 → 判定口径**。
> 「记录指标」里的每一项都要能落到 §6 的表格；不能落地的指标说明定义不清，需先改方案。

### S1 · 首次定位（50 个连接中定位某环境的同名库/表）

**准备数据**
- fixture 内建 `t51_trial.orders` 与 `t51_trial_b.orders`（**同名库名可不同、表名必须相同**：都用 `orders`）。
- 每款产品预建 **50 条连接**，其中 2 条分别默认到 `t51_trial` / `t51_trial_b`，其余 48 条指向 `bench` 或其它库，**连接名不得包含「b」「测试」这类提示**（避免靠命名猜）。
- 目标：打开 `t51_trial_b` 下的 `orders`。

**操作步骤**
1. 冷启动应用（退出后重启），窗口最大化。
2. 计时开始 → 用该产品**允许的最快路径**定位（搜索框 / 树 / 最近使用 / 命令面板均可）。
3. 双击打开 `orders`，等网格出现首行 → 计时结束。
4. 退出应用，重复 7 轮（首轮为冷，单列）。

**记录指标**：动作数（一次点击 / 一次键盘组合 / 一次必要确认各计 1；展开下拉再选项计 2）、误入率（前 3 次尝试里打开错连接/错对象的次数，任一次即记 1）、完成时间（首帧可交互）。

**判定口径**
- 必须打开的是**那条连接下**的 `orders`；表名相同，**靠连接身份判定对错**。
- 误入后自行纠正的轮次记为「误入 1 次」，时间照常记录（不计入「无差错轮」的 P50）。
- 报「误入率 = 误入轮数 / 7」与「无差错轮 P50」两个数，不许只报后者。

### S2 · 看表（窄表 / 200 列宽表；3000 / 10 万已加载行）

**准备数据**：`t51_trial.narrow`（8 列 × 10 万）、`t51_trial.wide200`（200 列 × 3000）。

**操作步骤**
1. 打开 `narrow` → 首行出现即可滚动（记「首次可交互」）。
2. 连续滚 10 屏（或用 End 到底）→ 记录滚动期间长帧。
3. 关闭，重开（热）→ 重复。
4. 打开 `wide200` → 把第 200 列滚到可见（或用列定位/列列表）→ 记动作数。
5. 静置 5 秒后记内存。

**记录指标**：首次可交互、滚动长帧比例、内存（打开前 / 首屏后 / 滚动后）、列定位动作数。

**判定口径**
- ⚠️ **必须先记录该产品是否分页/分批**（只取前 N 行 vs 流式）。若 `narrow` 只显示 1000 行，「首次可交互」不是同一件事 → 该产品此格记「口径不同（N 行）」，**不参与横向比较**。
- 长帧比例 = 连续 ≥2 帧无更新的次数 / 总滚动时长（60fps 基准）。
- 内存统一取「活动监视器 · 内存」列，进程族求和，采样点固定为「操作完成后 5s」。

### S3 · 看复杂值

**准备数据**：`t51_trial.val` 7 行，入库后用 `SELECT id, LENGTH(v)` 复核字节数：

| id | 内容 | 目标字节 |
|---|---|---|
| 1 | JSON 文本 | 100 KiB |
| 2 | JSON 文本 | 2 MiB |
| 3 | BIGINT | 值 `9007199254740993` |
| 4 | PNG（合法小图填充） | 100 KiB |
| 5 | PNG（合法小图填充） | 8 MiB |
| 6 | 普通 BLOB（随机字节） | 1 MiB |
| 7 | 长文本（含中文/emoji） | 256 KiB |

**操作步骤**
1. 逐行打开「查看完整值」（或该产品等价入口）。
2. 对 id=3 复制完整值，与 `9007199254740993` **逐字比对**。
3. 对 id=4/5 等待预览出现；对 id=6 记录是否给出 HEX/二进制视图；对 id=5 记录是否明确提示「过大/仅预览」。
4. 记录首次预览时间与解码后内存增量。

**记录指标**：原值保真（对/错 + 错成什么）、首次预览、解码后内存、失败状态（是否可见文案）。

**判定口径**
- **保真是硬判据**：`9007199254740993` 显示成 `…992` 直接判「不合格」，不参与时间比较。
- 「失败」必须是**可见文案 + 可复制原始字节**；空白面板、静默截断、把截断数据当完整数据保存，均判不合格。
- 8MiB 行若产品直接拒绝预览但**明确提示**，视为合格（能力边界不同，不是缺陷）。

### S4 · 小修改

**准备数据**：`t51_trial.orders`（60 行，有 PK）。

**操作步骤**
1. 双击某一格 → 改值 → 回车（标脏，**不提交**）。
2. 点列头排序。
3. 观察草稿是否还在；若弹确认，选「取消」。
4. 重新改 10 行同一列（用批量入口或逐格）→ 点保存 → 看预演。
5. 取消预演，确认无写入。

**记录指标**：是否丢草稿（是/否）、排序后草稿数、预演是否逐条可看（是/否/仅总数）、影响行数是否与实际命中一致、动作数、完成时间。

**判定口径**
- **丢草稿 = 一票否决**（该产品此场景记「不合格」，时间不再比较）。
- 影响行数：写 `UPDATE ... WHERE id=?` 的类型必须逐条显示；只给「共影响 N 行」视为「仅总数」。
- 「预演清晰度」只允许三档：逐条 SQL 原文 / 仅摘要 / 无预演。不允许打 1–5 分。

### S5 · 同名对象

**准备数据**：连接 A → `t51_trial`，连接 B → `t51_trial_b`，两库各有 `orders`（同结构、不同数据：A 的 `note` 以 `A-` 开头，B 以 `B-` 开头，便于事后判断串没串）。

**操作步骤**
1. A 连接下打开 `orders`，看第一行 `note`。
2. 切到 B 连接打开 `orders`，看第一行 `note`。
3. 在 B 连接下点「刷新结构」。
4. 在 B 连接下点「新建表」（**只看预填的库/连接，不执行 DDL**）。
5. 若支持 SQL 片段/收藏，在 B 下保存一条片段，回到 A 下看是否可搜到、归属显示什么。

**记录指标**：环境可辨（是/否）、串上下文（否 / 刷新 / 新建 / 片段）、动作数。

**判定口径**
- 用 `note` 前缀判定「打开的是哪一份」——**不靠标签文字判**（同名表标签文字一样）。
- 任何一步落到另一连接 → 记「串上下文」，并写明是哪一步。
- **不执行真实 DDL**（与 T03 的验收口径一致：看预演目标即可）。

### S6 · SQL

**准备数据**：无（用 fixture 现成表）。三条语句：
```sql
SELECT id, status FROM bench.big_table ORDER BY id LIMIT 100;   -- 一条
SELECT 1; SELECT 2; SELECT 3;                                   -- 三条
SELEC 1;                                                        -- 错误
SELECT SLEEP(20);                                               -- 取消用
```

**操作步骤**
1. 新建查询 → 输入一条 → 用该产品**宣称的**执行快捷键执行 → 记动作数与结果出现时间。
2. 输入三条 → 执行 → 看是全部执行还是只执行当前语句（记录实际行为，不预设对错）。
3. 输入错误语句 → 执行 → 看错误定位（行列号 / 高亮 / 仅消息）。
4. 执行 `SELECT SLEEP(20)` → 执行后 2 秒点取消 → 记取消耗时；在 fixture 侧 `SHOW PROCESSLIST` 确认查询真的消失。

**记录指标**：动作数、宣称快捷键是否正确触发（是/否）、错误定位（行列 / 高亮 / 仅消息）、取消耗时、取消是否真中断。

**判定口径**
- 「快捷键正确性」只看**该产品帮助里写的键位**是否真的生效，不拿我们的键位要求别人。
- 取消必须**服务器端消失**才算真取消；仅关闭 loading/结果区 = 「假取消」。
- 「一条/三条」的语义差异（执行全部 vs 当前语句）只记录，不评分。

### S7 · 文件（万条 INSERT）

**准备数据**
- `t51_10k.sql`：1 万条 `INSERT INTO t51_trial.file_target (status, amount, note) VALUES (...);`，UTF-8 无 BOM。
- `t51_10k_bad.sql`：同上，但**第 5001 条为非法语句**（用于测「遇错停止 / 跳过继续」与「已提交多少行」）。
- `t51_10k_gb18030.sql`：同 `t51_10k.sql` 内容转 GB18030（`note` 含中文）。
- 目标表 `t51_trial.file_target` 每次执行前 `TRUNCATE`。
- **事务设置必须记录**：脚本内**不含** `BEGIN/COMMIT`；记录 fixture 的 `innodb_flush_log_at_trx_commit` / `sync_binlog`，以及该工具是否自带批量事务（若工具有开关，统一设为「默认值」，并写明默认值是什么）。

**操作步骤**
1. 执行文件 → 记墙钟 → `SELECT COUNT(*)` 校验行数。
2. 重复 7 轮；首轮冷。
3. 用 GB18030 版重跑一次，检查中文 `note` 是否完好。

**记录指标**：真耗时（墙钟 P50/P95）、服务器耗时、吞吐（行/s）、失败行数、已提交部分（部分失败时 `COUNT(*)` 是多少）、编码正确性。

**判定口径**
- **不同 fsync / 事务设置下的数字不得并列**：若 A 工具逐条自动提交、B 工具 50 条一事务，必须在表里分两行记录，并注明「不可比」。
- 失败行：脚本里故意放 1 条非法语句（第 5001 条），看工具是「遇错停止」还是「跳过继续」，以及**已提交多少行**——这是语义差异，不是性能差异。

### S8 · 导出

**准备数据**：`t51_trial.export_src`（100 万行，含 `created_at DATETIME(6)`、`big_no` 部分为 `9007199254740993`、`payload` JSON、`note` 含 NULL 与空串各若干）。

**操作步骤**
1. 导出全表 → XLSX → 记耗时与内存峰值。
2. 导出筛选结果（`WHERE status='paid'`）→ 记是否导出「当前筛选」还是「全表」。
3. 导出「当前已加载」（若产品支持 `LIMIT 3000` 的视图）→ 记口径。
4. 对 100 万行导出发起后 5 秒取消 → 记残留（临时文件 / 子进程）。
5. 读回 XLSX：抽查日期、`big_no`、NULL vs 空串。

**记录指标**：耗时（P50/P95）、内存峰值、取消残留、读回正确性（日期 / 大整数 / NULL 与空串）、导出范围口径。

**判定口径**
- 正确性是硬判据：日期退化成裸数字（如 `43831.0000115741`）、大整数丢精度、NULL 变空串，任一出现即「不合格」。
- 「导出范围」必须写明是三选一：全表 / 当前筛选 / 当前已加载。**不允许**在记录里只写「导出」。
- 取消残留按「临时文件是否删除 + 子进程是否退出」两项计。

### S9 · 工作区

**准备数据**：15 个标签 = 6 张表（含 A/B 两个 `orders`）+ 4 个查询 + 5 个结果页。

**操作步骤**
1. 逐个打开 15 个标签 → 记动作数与总耗时。
2. 关闭其他（保留当前）→ 记是否一次完成。
3. 在 2 个表上各改 1 格（标脏）→ 退出应用 → 重启 → 看是否恢复标签与草稿。
4. 静置 60 秒，记空闲 CPU 与内存。

**记录指标**：标签管理动作数、草稿恢复（完整 / 不恢复 / 部分）、累计内存、空闲 CPU（60s 均值）。

**判定口径**
- 草稿恢复**只允许三档**，不允许「基本恢复了」。部分恢复要写清「哪一格丢了」。
- 空闲 CPU 取 60s 平均，不用瞬时值；采样工具与间隔固定（如 `top -l 12 -s 5`）。
- 15 个标签里必须包含**同名表跨连接**，否则测不出「标签来源」问题。

### S10 · 键盘（五焦点）

**准备数据**：同 S9；另备系统拼音输入法。

**操作步骤**（每个焦点各做一遍）
| 焦点 | 操作 |
|---|---|
| 树 | 选中表 → 按该产品宣称的「打开/刷新/删除」键 |
| 网格 | 方向键移动、⌘C、⌘V、⌘A、⌘Z、F2/Enter 进编辑 |
| 单元格输入 | 输入中文，**候选未上屏时**按 Enter；再按 Esc |
| SQL 编辑器 | 宣称的执行/格式化/注释键 |
| 模态（连接编辑器/导出对话框） | 开着模态按 ⌘T/⌘W/⌘S；候选未上屏时按 Esc |

**记录指标**：每个命令是否唯一响应（一次按键触发几个动作）、IME 误触次数、输入延迟（仅本场景做慢动作）。

**判定口径**
- 一次按键触发 ≥2 个动作 = 「多响应」，记失败；
- 候选未上屏时 Enter/Esc 触发了提交/关闭/删除 = 「IME 误触」，记失败；
- 中文输入测试必须用**真实输入法**手按（自动化无法替代，参见 `docs/engineering/T13-键盘矩阵验收清单.md:60-61`）。
- 输入延迟只对「按键 → 画面变化」做 5 次取中位数，不做 P95（样本太少）。

## 4. 执行顺序与工作量控制

建议顺序（先做判别力最强、最不容易受许可/口径影响的）：

```
S3（保真，硬判据） → S4（丢草稿，一票否决） → S5（串上下文） →
S6（SQL 语义） → S10（键盘/IME） → S2（性能） → S1（定位） →
S7（文件） → S8（导出） → S9（工作区）
```

理由：前五个是**语义正确性**，结果是「合格/不合格」，不依赖多轮统计，做完就能拿到结论；后五个是**性能**，需要 7 轮 × 4 产品，成本最高且最容易被口径毁掉。

**每款产品的单轮成本必须在执行前记录**（准备 50 连接、灌 100 万行、导出 XLSX 都很慢）。这些是**试验开销，不计入场景指标**。
