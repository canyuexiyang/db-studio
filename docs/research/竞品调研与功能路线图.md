>
> **定位红线（不变）**：**「反应最快的 macOS 数据库查看器」**，不是 Navicat 的功能对等平替。
> 目标用户是**间歇性查看/修改数据的开发者**，不是 DBA。
> **方法**：① 全量代码勘察（渲染层 40 文件 15111 行 + 20 个 core 包 + 主进程 9 模块 + 3 worker），核对「文档承诺」与「真实接线」的差距；② 对 8 款竞品做公开资料调研（含 2026-09-16 发布的 Navicat 18）；③ 按「单位成本的用户价值」排序产出迭代清单。
> **证据口径**：代码条目带文件路径与行号；竞品条目带公开来源（附录 B）。凡「组件存在但没接线」的一律显式标注，不把半成品当成已交付能力。

## 本轮更新（2026-10-12）：现行调研结论

本页仍是路线图唯一入口。详细证据见 [项目全景与竞品深度调研](项目全景与竞品深度调研-2026-10-12.md)：当前 0.6.0 工作区盘点、菜单/右键/快捷键清单、11 款竞品官方资料、任务级差距矩阵、16 项发现、29 项候选与验收标准。附件是调研建议，不是已批准需求。

**优先修可靠性，再补高频交互；暂不把 PostgreSQL / AI 当作下一轮默认方向。**

| 顺序 | 候选范围 | 原因 |
|---|---|---|
| 第一轮 | I01～I05、I28 | 未保存编辑保护、连接身份、值和 SQL 预览保真、冲突结果处理、快捷键/只读一致性、批删失败状态 |
| 第二轮 | I06～I13、I29 | 新空白行、标签/行号/SQL 右键、查询结果完整值、筛选可见性、复制入口和预演摘要 |
| 按使用频率选择 | I14～I24 | 撤销、JSON 树、图片查看、类型编辑、源行定位、导出语义、文件与结果管理等 |
| 暂缓战略投入 | I25～I27 | 参数模板、PostgreSQL、AI 需独立需求与成本论证 |

本轮实跑：typecheck 通过，50 文件 / 1639 单测通过，bundle 9/9 通过，独立 UI 回归 226/226 通过。完整 verify 在真库步骤因 `127.0.0.1:13306 ECONNREFUSED` 中止，后续链路未执行，不能称全绿。浏览器 DEMO 已复现排序丢未提交改动和对象列表混入另一连接同名库；其他发现按附件区分代码证据与待验证风险。

下文 2026-09-29 的完成状态与性能分数保留作历史记录。主观五维评分没有同机基准，**不再作为当前排名依据**；“组件/纯函数已实现”也不等于所有入口和异常闭环已交付。旧 W 板块交通灯结论以 v1.3 更正为准。§3.5 明确不抄清单和 PRD 非目标继续生效。

## 2.3 关键差距归因

### 差距 1：UI 层的「半成品」拉低实际可用性 ★最高优先级 → ✅ v1.2 P1-A 已解决

竞品没有这个问题 —— TablePlus 里 ⌘D 就是能用。DB Studio 当时有 9 处底层完整但没入口或传空函数，用户按键「毫无反应」却不知为什么。这是**投入产出比最高的差距**：不需要新设计、新依赖，不碰性能红线，纯接线。而它对「易用性」评分的伤害是实打实的 —— 用户按下 ⌘V 没反应，他不会知道「按钮能用」。

### 差距 2：缺「编辑交互的深度」—— 竞品把网格当电子表格 → ✅ v1.2 P1-B 已解决

DataGrip Top-9 里 5 条围绕「怎么让用户少写 SQL」：外键值即链接、SQL 表达式模式填值、Expand Selection、结果集转置、从结果集建表。Navicat 18 也加了 Batch Editing 与侧栏 Record Navigation。DB Studio 已有别人没有的**写操作安全护城河**（只提交脏单元格 + 逐条 SQL 预演 + 无主键只读），在这之上叠加编辑便利 = **既安全又顺手**，完全符合「查改数据闭环」北极星。

### 差距 3：缺「对象级上下文连续性」—— 每次操作都是孤岛 → ✅ v1.2 P1-C 已解决

竞品共同点是**操作之间能接力**：DataGrip 的 Go to Declaration / Highlight Usages / Refactoring；Navicat 的 Hover Info + Real-Time Error Detection；TablePlus 的变更审查历史 + 回滚。DB Studio 此前每个动作基本独立 —— 看不到「这条 SQL 里的 `user_id` 是什么类型」，不能点外键值跳过去，也没有偏好设置让习惯沉淀。

### 差距 4：多库支持是最大市场差距，但**不应在断层未清时动** → ⬜ 仍未启动

所有主流竞品都是多库，PG 在 PRD 里排 v1.1~v1.3。**但**：过早扩 PG 会把「一个半成品」变成「两个半成品」。当前 MySQL 链路已修圆满，PG 成为下一个合理的战略选项 —— 前置工作是**先落驱动接口抽象**（把 `core-driver-mysql` 拆出公共层），避免届时返工。这与实施顺序（MySQL 打样 → PG → Redis → Mongo，串行做透）一致。

### 差距 5：AI 已成为行业标配，但需谨慎进入 → ⬜ 仍未启动

- Navicat 18（2026-09）：Fill with AI / Ask AI / Fill Comment with AI，支持 ChatGPT/DeepSeek/Gemini/Ollama/Kimi/豆包
- DBeaver 26.x：AI Chat 成 core 能力（解释执行计划、AI 摘要、Model configurations）
- DataGrip 2026.2：3 个 AI Agent Skills + MCP 工具（list/create/edit database connection）
- Beekeeper：AI Shell

**建议路径**：只做「SQL 报错 → 解释错误 + 建议修复」这一个最高频痛点，默认关闭、用户自带 key 或本地 Ollama、走 fetch 不进首屏 bundle（守住 E2/S2 红线）。这是「借 AI 补短板」而不是「追 AI 热点」。

# 第四部分 · 落地建议与度量

## 4.1 执行顺序（已按此完成）

1. **第 1 批（V1→V2→V3→V4→V6→V7→V5）** —— 全是「把已有能力还给用户」，零架构风险，V5 偏好设置为后续新功能提供开关落点。做完后「实际可用性评分」从 3.5 拉到 4.2+，几乎不新增复杂度。
2. **第 2 批（V8→V11→V10→V13→V9→V12）** —— 网格深度。V8 冻结列是宽表查看刚需（已有行号 sticky 前提）；V11 几乎零成本；V10 对齐 2026 年竞品新特性；V13 复用现有安全链路。V9/V12 价值高但成本也高，可按需裁剪。
3. **第 3 批（V14→V15→V17→V16）** —— 上下文可读性。
4. **第 4 批（V18~V23）+ S/W 板块** —— P2 候选与编辑器/窗口增强。

## 4.2 不可破的红线（执行时逐条复核）

1. **性能**：每个改动后跑 `npm run verify`。新增 lazy UI 组件的外壳样式必须在 `styles.css` 首屏就位（红线 9）。
2. **体积**：新增任何依赖前先跑 `npm run check:bundle`。V10/V16/S 板块若引入解析库须重测 editor chunk ≤150KB gzip。
3. **写安全**：删行、表达式填值、批量编辑**必须全部走 `core-mutation` + SavePreviewModal 逐条预演**，不许有绕过路径。表达式是用户显式授权的值，要在预演 SQL 里原样展示。
4. **只读**：UI 置灰永远不算防线，只有 `core-sql-guard` 的 AST 白名单算。
5. **网格只读判定**：任何地方都不许自己判断有没有主键，只问 `isEditable()`。
6. **虚拟滚动纪律**：拖选、转置、冻结列的实现禁止滚动路径上的对象分配与 `decodeAll()`。
7. **范围纪律**：所有改动要么落在 PRD §三 非目标之外，要么先在 §三 登记。

## 4.3 度量口径（判断迭代有没有真的变好用）

| 指标 | v1.2 前基线 | 目标 | 怎么验 |
|---|---|---|---|
| ⌘V / ⌘⌫ 的实际触发成功率 | **0%（失效）** | 100% | ✅ e2e 断言已覆盖 |
| 快捷键触发占全部操作的比例 | 未采集 | 提升 | 埋点（默认关，开后才写本地） |
| 「改数据」闭环完成率 | 未采集 | 提升 | 埋点：保存预演 → 确认执行的转化率 |
| toast 报错率 | 未采集 | 下降 | 埋点分类 |
