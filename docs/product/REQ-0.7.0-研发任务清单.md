## 一、版本概览

### 1.1 版本目标

0.6.0 已有完整的连接、查表、筛选、编辑预演、SQL、导入导出和结构设计骨架。本轮**不做竞品功能数量追平，不重做视觉风格，不引入 PostgreSQL 或 AI**，价值集中在一点：

> 让已有能力在**连续操作**中保持**正确、可发现、可撤销、上下文清楚**。

推荐实施顺序（报告 §1）：

```
修正确性问题  →  补齐高频操作入口  →  增强值查看与编辑  →  完善查询和导出语义
```

四个衡量口径（报告 §2.1）：找到目标所需动作数、用户能否识别当前连接/库/表、改动是否可靠保留、等待与内存成本是否可控。

### 1.4 必须保留的既有约束（红线，不可在本轮改动中弱化）

简体中文 UI；Apple 原生精修风格；系统字体（不引入外部字体）；蓝灰色系（**禁止紫色/紫蓝渐变**）；内容区不透明（玻璃只在 Electron 侧）；原生交通灯（**不许自绘按钮**）；只解可视区；CodeMirror 首屏 0 字节 + 懒加载；主进程只读守卫；主键/唯一键安全定位（**无键表只读**）；脏单元格级更新（**绝不整行覆盖**）；写入前逐条 SQL 预演；BIGINT > 2^53 / NULL 与空串 / DATETIME(6) 微秒三件套保真；取消 = 真取消（KILL QUERY / kill utilityProcess）。

### 1.5 实施纪律与门禁

**开工前**：修 Bug 先写「能在当前版本失败」的复现，再改；新入口先定义目标对象与可用条件；不写没有证伪能力的断言（照旧实现写的断言要在错误输入上确认会红）。

**改动后必跑**：

| 场景 | 命令 |
|---|---|
| 任意代码改动 | `npm run typecheck` → `npm test` → `npm run check:bundle` → `npm run e2e:ui` |
| 数据层改动 | 对应专项 e2e（`e2e:grid` / `e2e:transfer` / `e2e:ssh` / `e2e:idle`） |
| 样式改动 | `npm run e2e:ui` + `node docs/design-mockups/verify.mjs`（浅/深双主题截图人工比对） |
| 窗口参数改动 | `npm run verify:traffic-lights`（像素级门禁，6 项） |
| 安装发行 | `npm run verify:installed`（22 项，含版本一致性断言） |
| 全量 | `npm run verify` |

**硬规矩**：未跑 `npm run verify` 不得宣告完成。`verify:installed` / `verify:traffic-lights` 不在 verify 链里，改对应代码后**单独跑**。装完新包首次跑 `verify:installed` 会撞 CDP 冷启动窗口，**不得误判为新包缺陷**。

### 1.6 任务编号与优先级说明

- 文档任务号 `T01`–`T52` 与事项系统编号 `1.`–`52.` 一一对应，**编号即建议执行顺序**。
- 优先级：`P0` = 先修（正确性/安全边界，一票否决级）；`P1` = 本版本优先；`P2` = 有需求再排。
- 成本档位（仅表示实现复杂度，**不是工期承诺**）：小 = 现有入口或状态修正；中 = 跨组件状态或新交互；大 = 驱动、数据模型、资源预算或安全语义变化。

#### T05 JSON 保真：去掉 parse→stringify 路径

- **报告引用**：§5 R04；§10 I03；§9.1 第一阶段；§5 V03/V04
- **问题点（代码 + 最小数值机制）**：`detail/CellValueModal.tsx:134` 的 `JSON.parse→JSON.stringify` 会把 `{"id":9007199254740993}` 格式化为 `9007199254740992`。原文仍保留，但**格式化显示/复制会失真**。
- **任务内容 / 功能点**：格式化不得先转 JS Number；显示原值与待提交值来源；超阈值退回原文并提供复制；**合法标量 JSON（无花括号）不被误判为普通文本**。
- **交付与验收样本**：超 2^53 整数、长小数、指数、Unicode 转义、重复键、深层对象、顶层 null/数字/字符串、非法 JSON、256Ki 字符上下边界、2MiB 以上值。
- **核验方式（重要）**：对格式化前后做 **token / 原文语义核验**，**不是** `JSON.parse` 后再比较——后者会掩盖同一种精度损失。

#### T19 新增空白行入口

- **报告引用**：§5 D16；§10 I06；§7「空表新增一行」

- **参考**：TablePlus `+Row`、Beekeeper `+`
- **依赖**：无

**实现与证据（2026-10-13）**

- **入口（4 处，全部复用同一条 `onAddBlankRow`，未新增写通道）**
  - 工具栏：`DataGrid` 工具栏最前 `data-testid="btn-add-row"`（禁用时给原因）；
  - **行号右键 / 单元格右键**：共用 `CellContextMenu`（行号右键的 `menu.column === ''`，本来就是同一份菜单），新项 `ctx-add-row` 排在「插入复制行」之前；
  - **原生菜单**：`action-catalog` 登记 `grid-add-row`（`scope: 'global'` —— 目录硬规则：局部动作不进原生菜单），`menu.ts` 的「数据」子菜单接线，渲染层 `event:menuCommand` 兜底；
  - **⌥⌘N**：`DataGrid` keydown（`meta && alt && KeyN`）。
- **计划器**：`core-mutation.buildBlankRowPlan(table)` —— 逐列判 `auto-skip | use-default | set-null | needs-input`；`INSERT INTO t () VALUES ()` 走 `PendingInsert.blank`。
- **DEFAULT 与 NULL 严格分开**：`use-default` 的列**不进 INSERT 列表**（让服务端 DEFAULT 生效），`set-null` 写显式 NULL。字面量 `"NULL"` 一律按「没有可用默认值」处理（fail-closed）。
- **预演防线**：显式 NULL 写进 `NOT NULL` 且无默认的普通列 → 预演即逐列点名拒绝，不让用户点确认后吃 MySQL 1048。
- **顺手修掉的真实缺陷**：`onDuplicateRow` 原用 `source.rowCount` 当新行下标，连按两次 ⌘D 会**落在同一行**（后者覆盖前者）。改为 `source.totalRows`，并为空白行加同款回归断言（脏格 6 → 12）。
- 🔴 **两个「测试从写出来就没验过」的坑（都靠真门禁才暴露）**
  1. `core-mutation` 那条「主键留空仍报主键原因」的断言，引用的 `codeKeyTable()` 定义在**另一个 describe 的函数作用域**里 → 实际跑的是 `ReferenceError`，红得毫无意义。已提到模块作用域，并补成「主键文案 / NOT NULL 文案**互斥**」的双向断言（同时验证该断言在错误输入上真的会红）。
  2. 新增的 `!col.isPrimaryKey` 过滤经变异测试确认**不可达**（`emptyPk` 分支在上方且会 `continue`）—— 保留为「对分支顺序的独立防线」，注释里如实写明它不承重，别让后来人以为是它在挡。
- 🔴 **真库门禁抓到的 P0 级缺陷：`INSERT INTO t () VALUES ()` 被自己的守卫拦死**
  - 现象：文本正确、单测全绿、UI 预演正常显示 —— 但真机执行时报「无法判定该写语句是否安全，已阻止执行（解析失败）」。
  - 根因：`node-sql-parser` 对「全默认值插入」的**三种合法 MySQL 写法全部解析失败** ——
    `INSERT INTO t () VALUES ()` ✗、`INSERT INTO t VALUES ()` ✗、`INSERT INTO t (c) VALUES (DEFAULT)` ✗。
    也就是说这不是「生成的 SQL 有问题」，而是守卫的解析器覆盖不到这条合法语法。
  - 修复（`core-sql-guard`）：**解析前的窄改写**（`normalizeBlankInsert`），只匹配「列清单为空 且 VALUES 全是空元组」的唯一形状，改写成 `(__dbstudio_blank_col__) VALUES (NULL)` 送进 astify ——
    **不是白名单放行**，AST 路径（类型白名单、多语句逐条判）照样生效。任何带值/带表达式的写法不匹配 → 照旧 fail-closed。
  - 与既有 `SET NAMES` 前置放行的区别：后者直接文本放行（失去 AST 覆盖）；这里保留 AST，只把解析器不认识的形态翻译成它认识的同义形态。
- **验收**
  - 单测：`core-mutation` 59/59（含 T19 buildBlankRowPlan 7 条 + INSERT 空列表 3 条 + NOT NULL 预演 2 条）；`core-sql-guard` **64/64**（新增 7 条，其中 5 条在「去掉改写」时变红，2 条负向对照两种状态下都必须绿）。
  - `e2e:ui` **246/246**（新增 12 条）：工具栏/右键入口可达、`dirty 0 → 6 → 12`（连点两次落在不同行）、预演逐列点名 `order_no/user_id/created_at`、可空列 `remark` 不被误伤、**被拒的行不生成任何 INSERT**。
  - `e2e:app` **60/60**（新增 10 条，临时库加 `blank_pure` 靶子）：真 meta 下核对 `auto-skip=[id] / defaulted=[status] / nulled=[note,ts] / needsInput=[amount,score,big_no]`；空白行生成的 SQL 文本**真的送到 MySQL 执行成功**，回读 `status='new' AND n=0` 命中 1 行、`IS NULL` 命中 0 行（两条一起判，避免空表上的空洞为真）。
- **文档**：本段 + 总表状态。

- **问题点**：导出范围口径不统一（表/筛选表、自定义查询、部分格式整库）；查询导出**在 worker 重查 SQL**，**不等于导出当前结果快照**，易遇数据变化 / NOW() / RAND() 差异。
- **任务内容 / 功能点**：统一「**选区 / 当前已加载 / 全部匹配 / 仅可见列**」口径，三者结果可验证；**快照 vs 重新查询明示**；排序 / 列范围一致。
- **约束**：不为格式数量继续加 YAML/HTML/XML。
- **参考**：Workbench 结果导出与整表导出分开

#### T41 SQL 文件打开与另存为

- **报告引用**：§5 Q11；§10 I20；§7「编辑本地 SQL 文件」；§12.3 第 3 条
- **问题点**：当前**无规范的 .sql 打开/另存为文件编辑闭环**，只有执行文件的路径。
- **任务内容 / 功能点**：打开文件**不执行、不自动跑**；编码处理；**未保存保护**；外部文件被覆盖时先处理冲突；**保存与执行明确分离**。
- **表述约束**：不得表述为「SQL 文件执行覆盖文件编辑」。
- **参考**：Postico 以文件组织 SQL 的完整体验

#### T42 固定/命名查询结果标签

- **报告引用**：§5 Q04；§10 I21；§4.5 结果标签行
- **问题点**：结果标签多结果、可关闭，但**缺固定/重命名/关闭其他管理**；结果越多越需要来源标识。
- **任务内容 / 功能点**：固定 / 重命名 / 关闭其他 / 复制 SQL；**新查询不覆盖固定结果**；来源 SQL / 连接 / 时间可追溯。
- **依赖**：T44（结果内存预算）
- **参考**：MySQL Workbench 结果标签菜单

#### T43 表布局记忆 / 视图方案

- **报告引用**：§5 F03；§10 I22；§7「保存这张表怎么看」
- **问题点**：筛选方案已有，但**列布局/排序分散**，不是完整表视图方案。
- **任务内容 / 功能点**：以**连接+库+表为键**保存表视图（筛选 + 排序 + 列布局）；列删除可恢复；**不误共享到其他环境**。
- **约束**：不能恢复旧数据；避免重复模型（复用已有筛选方案）；不照搬 Navicat table profile 全量。
- **依赖**：T26

#### T44 结果加载上限与按需大值

- **报告引用**：§5 Q07、V05；§10 I23；§9.2「大 BLOB」；§7「巨大 BLOB 打开」
- **问题点**：虚拟网格只控制 DOM，**普通查询仍把结果收集后编码**，不代表内存无界问题已解决；**巨大 BLOB 随结果进入内存**。
- **任务内容 / 功能点**：元数据 + **按需取值**；**有硬预算**；大查询可取消；**不自动改写任意 SQL 破坏语义**；无可靠行定位键时按需重取**不猜行身份**。
- **成本**：**大**。需驱动 / codec / 内存基准，**开工前先出实测数据再定方案**。
- **风险**：本轮尚未验证——并发查询响应先后导致旧结果覆盖新结果、多个大结果标签累计内存。

#### T45 手动更新入口收尾

- **报告引用**：§5 A02、R14；§10 I24；§7「自动升级」；§12.3 第 2 条
- **问题点**：有检查逻辑，但发布记录明确**缺 publish/app-update 配置**，不能称自动更新完整交付。
- **任务内容 / 功能点（自用口径）**：**未配置 / 失败 / 可更新 / 最新**四态真实；提供准确提示 + **手动下载入口**。
- **约束**：本轮**不做**签名/公证/完整发行链（若做完整链则另拆大任务）；**状态必须诚实**，不能提示「已是最新」而实际未接入。

## 五、问题点汇总（按严重度）

### 5.1 P0（4 项，必须先写失败用例再修）

1. **R01 / T01** — 排序等重载入口**静默丢弃未提交改动**。这是用户数据可靠性的直接损失。
2. **R02 + R03 / T02、T03** — **同名库跨连接串上下文**：清单混入、建表可能指向另一环境（生产误操作风险）。
3. **R04 / T05** — **JSON 大整数精度失真**（`9007199254740993` → `9007199254740992`），属数据保真红线（BIGINT > 2^53 不丢精度）。
4. **R15 / T08–T10** — **冲突行被静默吞掉且草稿无条件清空**；`interpretResult` 定义完整却**没有接线**，是确定的接线缺口。

### 5.2 P1（9 项）

R05（快捷键同键异义/三义）、R06（片段身份不含库/连接）、R07（问号参数误替换）、R08（手拼标识符）、R09（DDL 部分成功被掩盖）、R10（只读状态不统一）、R16（SQL 结果值查看无效入口），以及由 I 清单引入的高频入口缺口（新增行/行号右键/标签右键/SQL 右键/复制组织/列头快筛/筛选条件条）。

### 5.3 P2（3 项）

R11（打开源表丢上下文 + 文案误导）、R12（完整值传原值易复制旧值）、R13（类别 extras 接线不一致）、R14（更新链不通）。

### 5.4 本轮尚未验证的风险（**不得当作已复现缺陷计数**，需专项用例）

- 并发查询响应先后导致**旧结果覆盖新结果**；
- 多个大结果标签**累计内存**；
- 连接只读状态**切换时**的既有编辑；
- **图片解码失败**回退；
- **脚本事务分批遇 DDL / 用户事务语句**的边界。

### 5.5 其他需专项核对的点

- **S02**：不应把 MySQL DDL 批次当成可原子回滚的普通 DML；批量删表失败反馈需专项核对（T30）。
- **Q07**：虚拟网格控制 DOM 与「结果集整体内存」不是同一个问题（T44）。
- **X09**：脚本提速的 10 倍是**离线外推**，不能当真实同机胜过 Navicat 的依据（T52 待人工复核）。
