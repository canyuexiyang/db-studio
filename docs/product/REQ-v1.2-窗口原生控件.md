## 🔴⚠️ 更正（2026-09-29）：本文 §一 的核心结论【已被证伪】

**本文声称「原生交通灯已经存在，只是内容区没给它留位置」—— 这个结论是错的。**

真机实测（用户截图像素分析 + 6 组独立 Electron 进程探针对照）证明：
在 `transparent:true + frame:false` 组合下，**macOS 原生交通灯根本不渲染**。
`setWindowButtonVisibility(true)` 调用成功、不抛异常、`typeof` 判空也通过 ——
但灯就是没有。这是典型的**静默无效**：所有"接口层面"的检查都是绿的。

所以 W 板块当时做的全部工作（`.sidebar-head` 让位 78px、`.traffic-light-safe` no-drag 层、
W2 关闭拦截、W3 全屏语义）**让的是一块空白的地方**。用户报的「窗口无法关闭/缩小/放大」
不是布局问题，而是控件不存在 —— 只能靠 ⌘W 菜单或强杀进程。

**修复与完整实测证据见 [`REQ-v1.3-缺陷清理.md`](REQ-v1.3-缺陷清理.md) §六**，要点：

| 配置 | 交通灯 |
|---|---|
| `frame:false` + `transparent:true`（W 板块采用） | ❌ 无 |
| `titleBarStyle:'hidden'` + `transparent:true` + 玻璃 + `trafficLightPosition` | ✅ 有 |
| `titleBarStyle:'hidden'` + `roundedCorners:false` | ❌ 无（该参数单独就能让灯消失） |

**连带影响**：换用 `trafficLightPosition` 构造参数后，灯的渲染几何与旧
`setWindowButtonPosition` **不同**（直径 12px → 14px，占位 x∈[10,62] → x∈[16,76]）。
本文 §一 与 `e2e-app.mjs` W 板块里按旧几何写死的坐标断言已同步更正。

📌 保留本文的价值：W2（关闭拦截走询问-答复而非主进程自判脏数据）、
W4（no-drag 层的原因）、以及「不自绘按钮」的决策依然成立且已生效 ——
被推翻的只是 §一 对**灯是否存在**的事实判断。

## 一、🔴 先澄清现状：原生交通灯【已经存在】，问题在内容区没给它留位置

> ⚠️ **本节结论已作废，见文首更正。** 原文保留以存档当时的勘察过程与错误推理。

这是本次勘察最重要的发现，需要在动工前讲清楚，否则会把「已有能力」当成「从零开发」，方向会跑偏。

### 1.1 已经有了什么

`apps/desktop/src/main/window.ts:127-137`：

```ts
// 交通灯：frame:false 下唯一可用且不抛异常的组合（S1 实测）
try {
  if (typeof (win as any).setWindowButtonPosition === 'function') {
    (win as any).setWindowButtonPosition({ x: 16, y: 14 });
  }
  if (typeof (win as any).setWindowButtonVisibility === 'function') {
    (win as any).setWindowButtonVisibility(true);
  }
} catch {
  // 交通灯不可用不影响主流程，静默降级
}
```

**也就是说：系统原生的三个彩色圆点已经在左上角渲染了**，且它们是真原生控件（由 macOS 窗口服务器绘制），点击行为由系统提供，理论上已经能用。

### 1.2 那为什么用户觉得「没有」？

看渲染层 `apps/desktop/renderer/src/styles.css:180-200`：

```css
.toolbar {
  height: 38px;
  ...
  padding: 0 10px;          /* ← 左侧只留 10px */
  -webkit-app-region: drag; /* ← 整条工具栏都参与窗口拖拽 */
}
```

而 `App.tsx:1908-1912` 的第一个子元素就是：

```tsx
<div className="toolbar">
  <button onClick={() => setPaletteOpen(true)}>
    <IconSearch size={11} />
    命令面板 ⌘K        {/* ← 紧贴左边缘 */}
  </button>
```

交通灯中心位于 **x=16, y=14**，标准直径约 12px、间距约 8px，三个灯横向占据约 **x ∈ [10, 62]** 的区域；工具栏第一个按钮从 **x=10** 开始。

**结论：「命令面板 ⌘K」按钮与交通灯区域直接重叠。** 用户的实际观感是 —— 左上角那三个灯像是「压在按钮上的异物」，或者干脆看不见（被后绘制的按钮盖住），自然认为「没有」。

外加一条：`-webkit-app-region: drag` 铺满整条工具栏，会吞掉该区域的鼠标 hover —— 而 macOS 原生交通灯的 **hover 显示符号**（`✕` `─` `＋`）依赖 hover 事件，这里很可能失效。

## 二、需求（EARS）

### W1 内容区为交通灯预留安全区 ★核心

- **While** 窗口处于常规态（非全屏），系统应在内容区左侧保留一块不被任何交互控件占用的安全区，宽度不小于 **72px**。
- 安全区必须覆盖交通灯的完整几何范围（含 hover 态尺寸变化）。
- 安全区**不得**是「放一个透明占位 div」这种会随 UI 重排失效的做法 —— 应作为 `.toolbar` 的结构性 padding，并在 `styles.css` 里注明「这 72px 是给 macOS 原生交通灯的，不要删」。

> 为什么是 72px：交通灯在 x=16 起始，三灯 + 间距约 52px，右侧留 4px 呼吸 + 与原设计的 10px 内边距合并取整。最终以**真机截图测量按钮左边缘与灯的右边缘不相交**为准。

**验收**：`e2e:app`（dist 真机产物）新增断言 —— `.toolbar` 的第一个可聚焦子元素的 `getBoundingClientRect().left` ≥ 72；截图肉眼复核无重叠。

---

### W2 三个按钮行为接线

**先做一次真机确认**（见 §四 P0 步骤）：macOS 原生交通灯的点击行为在 Electron `frame:false` + `setWindowButtonVisibility(true)` 下**是否天然可用**。

- **If** 原生点击已生效 → W2 只需做 W1 的布局修复 + 补 hover 符号可用性验证，**不写一行窗口控制代码**。
- **If** 原生点击未生效（被 `app-region:drag` 吞掉或 Electron 实现差异）→ 需补 Behaviors 等价实现：

| 按钮 | 期望行为 | Electron API |
|---|---|---|
| 关闭（红） | 关闭主窗口；有未保存改动时走**既有脏标签关闭拦截**（`App.tsx:976-983`），不得静默丢数据 | `win.close()` |
| 缩小（黄） | 最小化到 Dock（macOS 标准「缩略」动画） | `win.minimize()` |
| 放大（绿） | 见 W3 | 见 W3 |

> 🔴 红线：若走 IPC 自实现，**关闭链路必须复用既有的关闭拦截**（`requestCloseTab` / `beforeCloseTab`），不许新开一条「直接 kill 窗口」的路径 —— 会绕过保存预演红线。

---

### W3 放大语义对齐 macOS ★易被人错

这是「原生观感 5.0」产品最容易翻车的一处：

macOS 的绿色按钮**默认行为是进入全屏（Full Screen）**，而**按住 ⌥（Option）再点击**才是「放大（Zoom / 最大化到可用空间）」。Windows/Linux 用户习惯的「点一下就最大化」在 macOS 上是错的。

- **When** 用户点击绿色按钮 → 系统应进入 macOS **全屏**（`setFullScreen(true)`），而不是贴边最大化。
- **When** 用户按住 `⌥` 点击绿色按钮 → 系统应切换到 Zoom（最大化到可用空间）。
- 双击工具栏空白区（`-webkit-app-region: drag` 区域）的 macOS 标准行为也应对齐：**「最小化/还原」取决于系统「连按两次窗口标题栏」设置**，这一点建议至少不要与系统行为冲突。

> 若 §四 P0 确认原生点击已完全覆盖了这套语义，**W3 直接验收通过，无需任何代码**。这恰恰是保留原生控件而非自绘按钮的价值。

---

### W4 hover 显示符号

macOS 原生行为：鼠标移入交通灯区域时，三个圆点上淡入显示 `✕` `─` `＋` 符号。

- **When** 鼠标悬停在交通灯区域时，系统应显示对应符号。
- 若该行为被 `-webkit-app-region: drag` 吞掉 → 需把交通灯所占矩形标记为 `no-drag`。

**注意**：`-webkit-app-region: drag` 与 `no-drag` 的取舍要小心 —— 拖拽区是用户移动窗口的主要手段，缩小它的面积会让窗口难拖。建议只在交通灯的精确矩形上打 `no-drag`，其余拖拽区保持不变。

## 三、🚫 明确不做：自绘三个按钮

用户说「补充三个原生操作能力」，但**正确的实现方式不是自绘按钮**，理由是：

| 自绘的代价 | 说明 |
|---|---|
| **丢 phototype 一致性** | macOS 27 的交通灯有圆角、渐变、hover 符号淡入、非激活窗口灰显、全屏态 hover 才浮现等一堆系统级行为，自绘只能做到「看起来像」，-hover/非激活/全屏态必露馅 |
| **违反既有决策** | 本项目特意选了 `frame:false` + `setWindowButtonVisibility`，就是为了拿原生控件（`window.ts:11` 注释：「交通灯用 setWindowButtonPosition + setWindowButtonVisibility」） |
| **违反设计红线** | 设计基调是「Apple 原生精修」（AGENTS.md §六），自绘交通灯与之相悖 |
| **白做它的替代品** | 系统已经画好了，我们只需要让开位置 |

**结论**：本板块的真实工作量 90% 在 **W1 布局让位**，而非「实现按钮」。

## 四、交付步骤

### P0 真机现状确认（半天，必须先做）

在做任何改动之前，用一个最小验证回答三个问题：

1. 原生交通灯在 dist 真机产物里**是否可见**？（用 Playwright 无法穿透到窗口服务器层，需要 `docs/design-mockups/shot.mjs` 或系统截屏）
2. 三个按钮**点击是否生效**？分别是全屏还是最大化？
3. hover 时**是否显示符号**？

> ⚠️ 这一步不能省。它决定了 W2/W3/W4 是「零行代码」还是「要写 IPC」。跳过直接自绘 = 用 10 天做一件本可以 0.5 天完成的事。

### P1 W1 布局让位（1 天）

改 `.toolbar` 的左侧 padding；核验 `App.tsx:1908` 起的首个按钮不再重叠；深/浅双主题截图复核。

### P2 W2/W3/W4 按 P0 结论处理（1-3 天）

- 原生可用 → 只补回归断言

### P3 回归（0.5 天）

## 六、风险与注意事项

1. **`setWindowButtonPosition` 是 Electron 的非标 API**，不同版本行为可能有差异 —— 这也是 `window.ts:129` 要 `typeof` 判空并 try/catch 的原因。改动时保留这层防御。
2. **降低 XCTDarwin 版本**：全屏是 macOS 的 Spaces 行为，全屏时交通灯会移出并 hover 才出现 —— 这是正常的，不要当成 bug 去「修复」。
3. **↔ 与 V5 偏好设置的交互**：若后续偏好设置里加了「隐藏/显示交通灯」之类的选项，属于超出本需求，未经批准不要加。
4. 本板块改动面虽小，但**触碰窗口形态**，务必在 dist 真机产物上验证，只跑 dev/浏览器 demo 是验不出来的（demo 模式根本不是 Electron 窗口）。
