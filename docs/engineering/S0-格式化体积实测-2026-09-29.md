# S0 决策门：SQL 格式化「体积实测」报告

- 日期：2026-09-29
- 决策对象：SQL 编辑器要不要做格式化、用什么做
- 被测自研产物：`packages/core-sql-editor/src/formatter.ts`（依赖 `tokens.ts`，两个一起进 chunk）
- 预算口径（来自既有 S0 约束）：编辑器 lazy chunk 现 **119.1 KB gzip**，预算 **150 KB**，**余量 30.9 KB**

---

## 1. 结论（先给答案）

**推荐方案 B（自研轻量格式化器），否决 A（引 sql-formatter），不维持 C。**

| 方案 | lazy chunk gzip 增量 | 占 30.9 KB 余量 | 判定 |
| --- | --- | --- | --- |
| A：引 `sql-formatter@15.9.0` | **+73.87 ~ 78.26 KB** | **239% ~ 253%**（超预算 43 ~ 47 KB） | ❌ 否决 |
| B：自研 `formatter.ts` + `tokens.ts` | **+4.13 KB** | **13.4%** | ✅ 推荐 |
| C：维持否决，不做格式化 | 0 KB | 0% | ❌ 不必 |

两个关键数字：**自研 gzip 增量 4.13 KB**（4,227 B）；**sql-formatter gzip 增量 73.87 KB**（75,646 B，已 tree-shaking 后的最优口径）。

## 2. 判定规则（先定规则，再看数据，避免事后找补）

以「新增 lazy chunk 的 **gzip** 增量」对「30.9 KB 余量」的占比为准（gzip 而非 raw，因为预算本身就是 gzip 口径）：

| 占比 | 判定 |
| --- | --- |
| ≤ 余量的 1/3（≤ 10.3 KB） | **直接选 B**：成本可忽略，功能照做 |
| 1/3 ~ 1× 余量（10.3 ~ 30.9 KB） | 需评审：要么裁剪（按方言/功能拆异步子包），要么降级为「仅格式化选中片段」 |
| > 余量（> 30.9 KB） | 维持 C，或把格式化挪出 lazy chunk（例如丢给主进程 / 按需 fetch 远端资源）后再议 |

按数据落位：A 落在「> 余量」区间且是余量的 2.4 倍以上 —— 单次引入就会把 E2 的编辑器体积预算击穿，且没有任何现实裁剪手段（见 §5 的 tree-shaking 实测：只 `import { format }` 也只从 78.26 KB 降到 73.87 KB，方言表与 lexer 是强耦合的）。B 落在「≤ 1/3 余量」区间 —— 直接放行。

## 3. 实测方法与口径（可复现）

所有数字都在 **`fs.mkdtemp(path.join(os.tmpdir(), 's0-'))`** 里跑完即删，仓库内不留任何 scratch 产物；脚本用 `node:child_process` 调本地 CLI，未向仓库 `package.json` 增删任何依赖。

| 项 | 口径 |
| --- | --- |
| 打包器 | 仓库自带 **esbuild 0.28.2**（`node_modules/.bin/esbuild`），未新增依赖 |
| 打包参数 | `--bundle --minify --format=iife --target=es2020 --legal-comments=none`（另测 `--target=esnext` 作参考） |
| gzip | `gzip -9 < file \| wc -c`。**走 stdin 是刻意的**：`gzip -c file` 会把文件名塞进 gzip 头，文件名长度不同会带来 ±7 B 的假差异 |
| 方案 A 取数 | ① 官方预构建产物 `dist/sql-formatter.min.js`；② 在 scratch 里 `npm i sql-formatter@15.9.0` 后，只 `import { format }` 再让 esbuild tree-shaking —— ② 是**对 A 最有利**的口径 |
| 方案 B 取数 | `formatter.ts` 作为入口（它 `import './tokens.js'`，两者必然同 chunk）；另测「只 `import { formatSql }`」的真实接线形态 |
| 版本 | sql-formatter **15.9.0**（2026-09-29 `npm view sql-formatter version`）；Node v22.22.2；macOS darwin-arm64 |

## 4. 实测数据

| 编号 | 产物 | raw 字节 | raw | gzip -9 | gzip | 占余量 |
| --- | --- | --- | --- | --- | --- | --- |
| A1 | sql-formatter 官方 `dist/sql-formatter.min.js` | 319,633 | 312.14 KB | **80,138** | **78.26 KB** | 253.3% |
| A2 | sql-formatter，esbuild tree-shaking（仅 `import { format }`） | 293,701 | 286.82 KB | **75,646** | **73.87 KB** | 239.1% |
| B1 | 自研 formatter+tokens（es2020） | 11,110 | 10.85 KB | **4,227** | **4.13 KB** | 13.4% |
| B2 | 自研 formatter+tokens（esnext） | 10,893 | 10.64 KB | 4,111 | 4.01 KB | 13.0% |
| B3 | 自研，真实接线（只 `import { formatSql }`，es2020） | 11,114 | 10.85 KB | **4,231** | **4.13 KB** | 13.4% |
| C | 不做格式化 | 0 | 0 | 0 | 0 | 0% |

补充观察：

- **A 的 tree-shaking 几乎没有用**：286.82 KB → 仍 73.87 KB gzip。sql-formatter 的 lexer / 方言表 / 表达式规则是整体引用的，只调 `format()` 也甩不掉另外 20+ 种方言。想把它压进 30.9 KB 余量，只能自己 fork 裁剪方言，维护成本远高于写一个 4 KB 的 formatter。
- **B 的 tree-shaking 同样没用**（B1 ≈ B3）：`canFormat` 与 `DELIMITER_REASON` 是给 UI 用的，本来就要导出，4.13 KB 是**保守上限**，不是理论下限。
- 自研版 gzip 后 4.13 KB 里，约 1.6 KB 是 `tokens.ts`（单独打包实测 3,479 B raw / 1,603 B gzip）。这部分**不是纯格式化成本**：分词器后续还要给语法高亮和错误诊断复用，摊薄后格式化的实际边际成本更低。
- 性能（同一批样本顺带实测，详见 `formatter.test.ts`）：一条 6.3 KB SQL 的「分词 + 格式化」合计 **2.7 ms**，远低于 50 ms 的验收线；且 `canFormat` 与 `formatSql` 都是纯函数，可放进 lazy chunk 异步加载，不阻塞编辑器首屏。

## 5. 能力对照（诚实版：sql-formatter 支持、自研版不支持的清单）

**自研版明确不支持**（不要对外吹）：

| 能力 | sql-formatter 15.x | 自研 |
| --- | --- | --- |
| 方言数量 | 20+（mysql / postgresql / sqlite / bigquery / snowflake / tsql / plsql / hive / spark / redshift / db2 / trino…） | **仅 MySQL 口径**（`-- ` 注释、`#` 注释、反引号、`\` 转义） |
| 关键字/函数名/数据类型/标识符 大小写 | 四类可分别配置（`keywordCase` / `functionCase` / `dataTypeCase` / `identifierCase`） | **仅 `keywordCase`**；函数名与标识符一律原样（刻意：避免改写用户自定义函数名） |
| 表达式宽度 & 密集算子 | `expressionWidth` / `denseOperators` | 只有 `maxLineWidth`，且是「尽力而为」，不严格 |
| 列表排版风格 | `tabular`（按 `=`、列对齐）/ `standard` | 只有一种：子句换行 + 列表项缩进一级 |
| `CASE WHEN / END` 缩进 | 支持（`WHEN` / `ELSE` 单独缩进） | **不支持**，`CASE ... END` 整段内联 |
| 窗口函数 `OVER (...)`、CTE 缩进美化 | 支持 | **不支持**（`WITH cte AS (...)` 只当普通子查询展开，可用但不漂亮） |
| DDL（CREATE TABLE 列定义对齐、ALTER、索引） | 支持 | **不支持**，只做最小处理（`CREATE TABLE t (...)` 原样内联） |
| 参数占位符（`?` / `:name` / `@var` / `$1`） | `paramTypes` 可配 | 只分词不特殊排版（`?` 归 `unknown`，原样输出） |
| 块注释内部重排、注释前后空行控制 | 支持 | **不支持**，注释一律原样保留（这是刻意的：见 §6） |
| 存储过程 / 触发器体（`DELIMITER`） | 部分方言支持 | **明确拒绝**并给出中文原因（与 `index.ts:15` 既有决策一致） |
| 语法校验 / 报错定位 | 遇到无法解析的结构会抛错 | **不做校验**，畸形 SQL 原样返回 |

**自研版反而更强 / 更契合本项目的三点**（不是吹，是约束不同）：

1. **零依赖、4 KB**：不引入 74 KB 的方言表，直接守住 E2 体积预算。
2. **DELIMITER 是「明确拒绝 + 中文原因」，不是「尽力解析」**：DB Studio 的 §6.4 不打算支持存储过程脚本，静默格式化成错的东西比拒绝更糟。
3. **与 `tokens.ts` 同层复用**：分词器一份，格式化 / 语法高亮 / 后续错误诊断共用，不会出现「高亮认为这是字符串、格式化认为这是注释」的分裂；sql-formatter 是黑盒，拿不到 token 流给高亮用。

## 6. 已知风险与后续动作

- **风险 1（低）**：`maxLineWidth` 是启发式，个别超长单行不会强制拆开。验收口径定位为「可读性」，不是「严格 80 列」。
- **风险 2（低）**：`CASE WHEN` / CTE / DDL 排版朴素。若后续 REQ 明确要求，再按同一个 token 流扩展，不需要换方案（A 的体积门槛已经把「换成 sql-formatter」这条路封死了）。
- **风险 3（中）**：接线（alias、index.ts re-export、渲染层调用、快捷键）**尚未做**，本报告只覆盖纯逻辑层与体积判定。接线后需在真机上复测一次 lazy chunk 体积，确认实测增量与本报告 4.13 KB 的偏差在 ±1 KB 内。
- **后续动作**：本次交付的 `tokens.ts` / `formatter.ts` 及其单测（93 个 it，含幂等、语义不变、性能断言）已可独立验收；体积结论在接线复测后回填本文件。
