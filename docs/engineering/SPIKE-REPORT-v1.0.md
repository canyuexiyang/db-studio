## 一、S1（决策性）：透明玻璃窗口 × 虚拟网格滚动 FPS

> 完整报告：`spike/s1-glass-grid/RESULTS.md`

### 1.1 实测数据（5 轮 × ≥600 帧，程序化滚动，P50/P95）

| 组 | 窗口配置 | 网格 | **P50 FPS** | P95 FPS | 掉帧率 |
|---|---|---|---|---|---|
| **G1** | `transparent:true` + `bg #00000000` + `roundedCorners:false` + `frame:false` + **`createWindowGlass(win,{kind:'glass'})`** | 10000×20 | **120.5** | 133.3 | **0%** |
| **G2** | 同上但**不加玻璃**（隔离"透明"变量） | 10000×20 | **120.5** | 131.6 | **0%** |
| **G3** | `transparent:false`（不透明对照，vibrancy 关） | 10000×20 | **120.5** | 131.6 | **0%** |
| **G4** | 不透明 + 仅 100 行（120Hz 上限校验） | 100 行 | **120.5** | 131.6 | **0%** |

### 1.2 判定（按 PRD §8.1.1 判定表，工程可直接执行，无需再评审）

| 项 | 值 |
|---|---|
| 实测日期 | **2026-09-21** |
| 透明 + 玻璃 P50 / P95 FPS | **120.5 / 133.3** |
| 不透明对照 P50 / P95 FPS | **120.5 / 131.6** |
| **判定采用方案** | **A**（整窗原生玻璃 + 内容区不透明） |
| **D4 是否达成** | **✅ 达成** |

### 1.3 B1 冲突：不成立

- **决定性证据是 FPS 差分**：G1（透明+玻璃）与 G3（不透明）**完全相等（120.5 vs 120.5，掉帧率均 0%）**。若 B1 成立（透明→软件合成→FPS 崩），G1/G2 应显著低于 G3 —— 未观察到。
- **GPU 证据**：GPU 设备 `ANGLE (Apple, ANGLE Metal Renderer: Apple M5 Pro)`；`chrome://gpu` 显示 Canvas / Compositing / Rasterization / WebGL 全部 `Hardware accelerated`。
- **诚实边界**：`chrome://gpu` 是全局视图，不反映单个透明窗口的 compositor 选择；但 FPS 差分已自证无退化（影响 < 0.1ms，远在 120Hz 帧预算 8.33ms 内）。

### 1.4 落地要点（必须写进产品代码）

1. **玻璃包是 ESM-only**：`exports` 只声明 `import`，`require()` 会抛 `ERR_PACKAGE_PATH_NOT_EXPORTED`。`GlassProvider` 必须 `await import()`。
2. **交通灯**：`frame:false` 下用 `setWindowButtonPosition` + `setWindowButtonVisibility`（实测可用且不抛异常）；**`titleBarStyle` 仅 `frame:true` 可用**，与玻璃形态冲突，不要用。
3. **降级路径保留**：本机未触发，但作为跨机型保险保留（FPS<50 自动关玻璃）。

## 二、S5（决策性）：10M 行 fixture + 列式 IPC 首屏

> 完整报告：`spike/s5-fixture-ipc/RESULTS.md`

### 2.1 Fixture：可快速造出，且远快于预估

| 指标 | 实测 | 评审预估 |
|---|---|---|
| 造数方式 | 存储过程分批 `INSERT…SELECT`，每批 COMMIT | 同 |
| `big_table` | **10,000,003 行** | 1000 万 |
| `no_key_table` | 50,000 行（**无主键/无唯一键**，供红线测试） | —— |
| 灌数 + 建索引 | **≈2.5 min**（69s + 80s） | 10~20 min（**快 4~8 倍**） |
| 磁盘 | 卷 `dbstudio_mysql_data` 共 **5.8 GB** | 2~3 GB |
| 可复用 | ✅ named volume，后续所有性能验收共用 | 同 |

### 2.2 列式 vs JSON 对照（P50）

| 场景 | 形式 | 体积 | 编码 ms | 全量解码 ms | **只解可视区 40 行** |
|---|---|---|---|---|---|
| LIMIT 3000 | 列式 | 0.477 MB | 4.15 | 1.53 | **0.029 ms** |
| | JSON | 0.443 MB | **0.70** | 1.10 | 必须全量 1.10 ms |
| LIMIT 10000 | 列式 | 1.602 MB | 12.91 | 5.44 | **0.028 ms** |
| | JSON | 1.492 MB | 2.44 | 3.98 | 必须全量 3.98 ms |
| LIMIT 500000 | 列式 | 83.58 MB | 981.8 | 327.8 | **0.029 ms** |
| | JSON | 78.99 MB | 186.1 | 338.3 | 必须全量 338.3 ms |

### 2.3 ⚠️ 对技术评审论证依据的修正

评审 §2.2 称列式能把「15MB JSON 降到 2~4MB，传输耗时从数百毫秒降到十毫秒级」。**实测不支持这个论证**：

- 在 PRD 指定规模（3k/1万行 × 12 列紧凑数据）下，**列式体积反而略大**（0.477 vs 0.443 MB），**编码比 `JSON.stringify` 慢 3~5 倍**。原因：紧凑小数值在 JSON 里只占 1~7 字节文本，列式固定 8 字节数值 + 4 字节偏移。
- **列式的真实价值是**：① **只解可视区**（解码 40 行恒定 ~0.03ms，与结果集大小无关；JSON 到 50 万行已涨到 338ms）；② **渲染端内存有界**。
- **结论：列式方案保留**（与虚拟滚动天然契合），但论证依据应改为「**按需解码 + 内存有界 + 大结果集可扩展**」，而非"省体积/省序列化"。

### 2.4 三项预算判定（全部可达）

| 指标 | 预算 | 实测 | 判定 |
|---|---|---|---|
| 表首屏（1000万行表，LIMIT 3000） | ≤1000 ms | **8.4 ms** | ✅ 可达 |
| SQL 结果首行渲染（1万行） | ≤500 ms | **12.9 ms** | ✅ 可达 |
| 带索引字段排序 | ≤1500 ms | **6.9 ms**（`EXPLAIN` 确认命中 `idx_created_at`） | ✅ 可达 |

### 2.5 数据正确性抽查（红线，全部通过）

| 项 | 结果 |
|---|---|
| BIGINT > 2^53（9007199254740993）保持精确 | ✅ |
| `DATETIME(6)` 微秒位不丢失 | ✅ |
| JSON 字段内大整数不被二次解析损精度 | ✅ |
| DECIMAL 保持字符串、无浮点尾数 | ✅ |
| nullMask 正确 | ✅ |

## 三、S2（验证性）：冷启动骨架

> 完整报告：`spike/s2-coldstart/RESULTS.md`

### 3.1 实测（每组 5 次，取第二次及以后，P50）

| 组 | 配置 | P50（进程内） | **P50（spawn 口径）** | 判定 |
|---|---|---|---|---|
| **C1** 朴素 | 启动路径同步 require `mysql2`+`pg`+`ssh2`+`node:sqlite` | 247 ms | **297 ms** | ✅ |
| **C2** 懒加载 | 空壳窗口，依赖按需 | 225 ms | **269 ms** | ✅ |
| **C3** 打包 | C2 + electron-builder arm64 / asar 默认压缩 | **217 ms** | **265 ms** | ✅ **达标** |

**结论：≤1500ms 可达，实测 217~265ms，余量约 1283ms（85% 预算未用）。无需改为 ≤2.0s。**

### 3.2 阶段分解（P50）

| 阶段 | C1 | C2 | **C3** |
|---|---|---|---|
| exec → 模块顶部（Electron 运行时初始化，**固定成本**） | 63 ms | 62 ms | **63 ms** |
| 模块顶部 → `whenReady`（**唯一可懒加载影响的部分**） | 59 ms | 33 ms | **32 ms** |
| `whenReady` → 窗口创建 | 43 ms | 47 ms | **44 ms** |
| 窗口创建 → `did-finish-load` | 73 ms | 61 ms | **63 ms** |
| `did-finish-load` → 首次 paint | 9 ms | 17 ms | **17 ms** |

### 3.3 ⚠️ 与评审预估的偏差

评审 §5.1 称驱动懒加载是「**最大的一块**」「缺一件基本没戏」。**实测不支持**：三个驱动 + `node:sqlite` 全部同步加载**只花 26ms**（`moduleTop→whenReady` 59ms→33ms）。原因：`mysql2`/`pg` 是纯 JS，`ssh2` 默认走 JS 实现，M5 上解析极快。

**真正的固定成本**是 Electron 运行时初始化（63ms）+ 渲染进程启动（~107ms），合计约 170ms，占打包版总耗时的 **78%**，懒加载动不了。

### 3.4 建议：拆子预算（A3）

探针是空壳，没有 React/Zustand/CodeMirror。真实应用风险在**首屏 JS 体积**。建议：

| 子项 | 建议预算 |
|---|---|
| Electron 运行时 + 窗口 + 首屏 paint（本 Spike 基线） | ≤ 400 ms |
| 应用首屏 JS 解析 + React 提交 | ≤ 700 ms |
| 历史库打开 + 配置读取 + schema 快照加载 | ≤ 400 ms |
| **合计** | **≤ 1500 ms** |

并建议给「首屏 JS bundle 体积」设硬预算（≤1.5MB 未压缩）——这比纠结懒加载更能守住 1500ms。

## 四、S3（验证性）：100 万行 xlsx 导出

> 完整报告：`spike/s3-xlsx-export/RESULTS.md`

### 4.1 实测（每场景 3 次，P50；100 万行 × 12 列混合类型）

| 场景 | 配置 | P50 耗时 | 峰值内存 | 文件 | 类型保真 |
|---|---|---|---|---|---|
| E1 | exceljs 流式默认 | 10万行 **1.81 s** | 458 MB | 8.9 MB | ✅ |
| E2 | exceljs 流式默认 | 100万行 **20.28 s** | 2739 MB | 88.3 MB | ✅ |
| **E3** | **`useSharedStrings:false` + `useStyles:false`** | **6.26 s** | **987 MB** | 83.2 MB | ✅ **全通过** |
| E4 | 手写 sheet XML + archiver 流式 zip | **3.12 s** | 1166 MB | 89.3 MB | ❌ **日期退化** |

与公开基准（第三方，非 M5）对比：10万行 ~12s → 本机 **1.81s**；100万行 ~89s → 本机 **6.26s**（E3）。**M5 快 5~14 倍。**

### 4.2 预算重定

| 指标 | 原预算 | 实测 | 结论 |
|---|---|---|---|
| 100 万行耗时 | 待定（原 ≤30s，预备 ≤60s） | **6.26 s**（E3） | ✅ **保留 ≤30s**，无需退到 ≤60s |
| 峰值内存 | ≤500 MB | **987 MB**（E3） | 🔴 **不可达，建议改为 ≤1.2GB** |

> 评审预估「流式写入下 ≤500MB 应该很轻松（基准 92MB）」不成立 —— **92MB 是输出文件体积，不是进程内存**。exceljs 流式仍会在进程内累积 row 对象与 zip 缓冲区。
> 补充口径：导出运行在 **utilityProcess** 内，进程结束内存即释放，**不影响常驻内存 ≤250MB 指标**。

### 4.3 关键决策：采用 E3，不采用 E4

E4 比 E3 快 **2.0 倍**，但**日期类型损坏**：E3 读回为 `Date(2020-01-01T00:00:02.000Z)`，E4 读回为**裸数字 `43831.0000115741`**（写了 Excel 序列号但无 `numFmt` 样式）。

**「失去样式能力」的真实代价不是"不好看"，而是数据类型损坏。** 要修就必须补写 `styles.xml` + 单元格样式索引。E3 的 6.26s 已远优于预算，不值得为 2 倍加速牺牲正确性。E4 作为未来 >300 万行导出的备选，届时必须同时实现 `styles.xml`。

> 附带收获：E4 实现已包含 **32767 字符截断 + XML 非法控制字符清理**（PRD Q6 的 B 方案），应复用到产品导出路径。

### 4.4 utilityProcess「真取消」验证：✅ 通过

| 验证项 | 结果 |
|---|---|
| fork + `parentPort.postMessage` 通信 | ✅ 收到 10 条消息 |
| `kill()` 返回值 | ✅ `true` |
| 进程确实消失 | ✅ 探活失败 |
| **kill 延迟** | ✅ **6 ms** |
| 主进程存活 | ✅ |
| 停止写入 | ✅ kill 后 400ms 文件不再增长 |

⚠️ 配套要求：kill 后输出文件是**半截的**（实测 60 字节），产品必须**删除或标记未完成**，不能残留打不开的 .xlsx（PRD §八 已有该验收项）。

### 5.2 🔴 发现文档事实错误：Darwin 版本判断（A2）

`docs/engineering/TECH-REVIEW-v1.0.md` §3.2 与 `docs/archive/PRD-v0.4.md` §8.1 均写：

> "当前实测环境 macOS 27.0 (26A428) 对应的 Darwin 内核版本是 **26**，按 '27' 比较会判错"

**实测反驳**：

```
$ node -e "console.log(require('os').release())"   →  27.0.0
$ uname -r                                          →  27.0.0
$ sw_vers                                           →  ProductVersion 27.0, BuildVersion 26A428
```

**`os.release()` 返回的是 27.0.0（Darwin 27），不是 26。** 文档把 **build 号 `26A428` 误当成了 Darwin 内核版本号**。

| 来源 | 声称 | 实测 |
|---|---|---|
| 评审文档 / PRD | Darwin 26 | ❌ |
| `os.release()` / `uname -r` | —— | ✅ **27.0.0** |

**影响**：
- **判定阈值 `>= 26` 仍然安全**（27 ≥ 26 成立，玻璃正常启用），本次未造成功能问题——属于"错得幸运"。
- 但**文档事实必须更正**，否则后续按"Darwin 26"推导 macOS 版本映射会一路错下去。
- 建议表述：**用 `os.release()` 取 Darwin 内核主版本判断 `>= 26`；不要依赖 build 号推断，也不要假设 Darwin 主版本 = macOS 市场版本减一。**（历史映射参考：macOS 15→Darwin 24、macOS 26→Darwin 25、macOS 27→Darwin 27。）
- 阈值应集中定义为常量，不要散落在比较之外的地方。
