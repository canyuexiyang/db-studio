# Spike S3 结论报告：100 万行 xlsx 导出实测（性能预算重定）

> 验证性 Spike。实测日期：2026-09-21
> 环境：macOS 27.0 (26A428) / Apple M5 Pro 15核 / 48GB / arm64 / Node v22.22.2
> 数据：100 万行 × 12 列，混合类型（int / string / decimal / Date / boolean / NULL / 400 字符长文本）
> 每场景 3 次取 P50。约束严格执行 TECH-REVIEW §1.5：只测 `stream.xlsx.WorkbookWriter`，未使用 `writeFile()`。

---

## 0. 一句话结论

**原预算「100 万行 ≤30s」在优化配置下可达（6.3s），无需改成 ≤60s。** 但**峰值内存 ≤500MB 不可达**（实测 987MB~1.17GB），需重定。推荐：**exceljs + `useSharedStrings:false` + `useStyles:false`**（E3），不要为了速度选手写 XML（E4）——它快但会**丢日期类型**。

---

## 1. 实测对照表（P50，3 次）

| 场景 | 配置 | 行数 | **P50 耗时** | 峰值内存* | 文件体积 | 类型保真 |
|---|---|---|---|---|---|---|
| **E1** | exceljs 流式**默认** | 10 万 | **1.81 s** | 458 MB | 8.9 MB | ✅ |
| **E2** | exceljs 流式**默认** | 100 万 | **20.28 s** | 2739 MB | 88.3 MB | ✅ |
| **E3** | exceljs **`useSharedStrings:false` + `useStyles:false`** | 100 万 | **6.26 s** | **987 MB** | 83.2 MB | ✅ **全通过** |
| **E4** | **手写 sheet XML + archiver 流式 zip** | 100 万 | **3.12 s** | 1166 MB | 89.3 MB | ❌ **日期退化** |

\* 峰值内存：`process.memoryUsage().rss` 采样；E4 另用 `/usr/bin/time -l` 复核为 **848 MB**（与 rss 采样量级一致）。

### 与公开基准对比（第三方，非 M5）

| 行数 | 公开基准 | 本机 E2（默认） | 本机 E3（优化） |
|---|---|---|---|
| 10 万 | ~12 s | **1.81 s** | —— |
| 100 万 | ~89 s | **20.28 s** | **6.26 s** |

→ M5 比公开基准快 **5~14 倍**。**评审"100 万行 ≤30s 大概率不可达"的判断偏保守**：默认配置确实接近（20.3s，勉强达标），优化配置则大幅达标。

## 2. 预算重定结论

### 2.1 耗时：✅ 原预算「100 万行 ≤30s」**可以保留**

- E3（推荐配置）实测 **6.26s**，仅为预算的 21%，余量充足。
- **不需要**退到「≤60s」或「50 万行 ≤30s」——PRD R7 的预备口径可以收回。
- 但**必须**强制使用 `useSharedStrings:false` + `useStyles:false`：默认配置（E2，20.3s）虽仍在 30s 内，但已逼近上限，且内存不可接受（见下）。

### 2.2 峰值内存：🔴 「≤500MB」**不可达，建议重定为 ≤1.2GB**

| 场景 | 实测峰值 | vs 500MB 预算 |
|---|---|---|
| E1（10 万行） | 458 MB | ✅ 勉强达标 |
| E2（100 万，默认） | 2739 MB | ❌ 超 5.5 倍 |
| **E3（100 万，优化）** | **987 MB** | ❌ 超 ~2 倍 |
| E4（100 万，手写 XML） | 1166 MB | ❌ 超 ~2.3 倍 |

**评审预估"流式写入下 ≤500MB 应该很轻松（基准 92MB）"不成立**——92MB 指的是**输出文件体积**，不是进程内存。exceljs 流式写入仍会在进程内累积 row 对象与 zip 缓冲区。

**建议修订 PRD §7**：`导出 100 万行到 xlsx` 的峰值内存从 **≤500MB 改为 ≤1.2GB**。
依据：E3 实测 987MB，留 20% 余量取 1.2GB。补充口径——**导出运行在 utilityProcess 中，进程结束内存即释放，不污染常驻内存的 ≤250MB 指标**（这条已实测验证，见 §4）。

---

## 3. E3 vs E4：为什么推荐 E3（关键决策）

E4 比 E3 快 **2.0 倍**（3.12s vs 6.26s），但**类型保真失败**：

| 类型 | E3（exceljs） | E4（手写 XML） |
|---|---|---|
| int | ✅ | ✅ |
| decimal | ✅ | ✅ |
| boolean | ✅ | ✅ |
| string | ✅ | ✅ |
| **Date** | ✅ `Date(2020-01-01T00:00:02.000Z)` | ❌ **退化为裸数字 `43831.0000115741`** |
| NULL | ✅ | ✅ |

E4 的日期写成了 Excel 序列号但没有 `numFmt` 样式（手写 XML 不含样式表），读回时就是裸数字。要让日期正确，必须补写 `styles.xml` 并给单元格挂 `s=` 样式索引——**这正是"失去样式能力"的真实代价，不只是"不好看"，而是数据类型损坏**。

**结论：采用 E3。** E4 的 2 倍加速不值得用"日期变成数字"去换；且 E3 的 6.26s 已远优于预算。手写 XML 方案作为**未来若需 300 万行以上导出**的备选，届时必须同时实现 `styles.xml`。

> 附带收获：E4 实现中已包含 **xlsx 单元格 32767 字符上限截断 + XML 非法控制字符清理**（PRD Q6 要求的 B 方案），这段逻辑应复用到产品代码的导出路径。

## 4. utilityProcess「真取消」验证：✅ 通过

用 Electron 44.4.3 实测 `utilityProcess.fork()` + `kill()`：

| 验证项 | 结果 |
|---|---|
| fork 成功并通信 | ✅ 收到 10 条 `parentPort.postMessage` 消息 |
| `kill()` 返回值 | ✅ `true` |
| 进程确实消失 | ✅ `process.kill(pid, 0)` 探活失败 |
| **kill 延迟** | ✅ **6 ms** |
| 主进程存活 | ✅ 未被拖垮 |
| 停止写入 | ✅ kill 后 400ms 文件字节数不再增长 |

**结论**：导出放 utilityProcess 的「取消」是**真取消**（6ms 内终止），符合 PRD §7.1「可 `kill()`，因此取消是真取消」的承诺。

⚠️ **配套要求（PRD §八 验收项已有）**：kill 后输出文件是**半截的**（实测 60 字节），产品必须**删除该文件或明确标记为未完成**，不能残留一个打不开的 .xlsx。

## 5. 给 PRD 的具体修订建议

| 位置 | 现状 | 建议改为 |
|---|---|---|
| §7 性能预算 | 导出 100 万行 xlsx「待 Spike 重定（预备 ≤60s）」 | **≤30s（实测 E3 6.26s，保留原预算）** |
| §7 性能预算 | 峰值内存 ≤500MB | **≤1.2GB**（实测 987MB + 20% 余量）；并注明导出在 utilityProcess 内，不影响常驻 ≤250MB |
| §6.6 / §7.1 | 导出实现 | 强制 `stream.xlsx.WorkbookWriter` + **`useSharedStrings:false` + `useStyles:false`**；不用手写 XML（会丢 Date） |
| §12 验收 | —— | 保留「导出中途取消，输出文件不存在或标记为未完成」（已实测 kill 会留半截文件） |

## 6. 复现命令

```bash

RUNS=3 node bench-export.mjs          # E1~E4 全量，结果写入 raw/export-bench.json
```

原始数据：`raw/export-bench.json`、`raw/utility-kill.json`。

## 7. 诚实边界

1. 峰值内存用 `rss` 采样（50ms 间隔），可能略低估瞬时峰值；E4 用 `/usr/bin/time -l` 复核为 848MB，与 rss 采样量级一致，故认为 E3 的 987MB 可信。
2. 数据为**本地生成的合成数据**，非真实业务数据。真实数据若含更长文本或更多 NULL，耗时与内存会有偏差（长文本偏慢、NULL 偏快）。
3. 未测 CSV / JSON / SQL 导出格式（不在 S3 范围）。
4. E4 的 zip 用 `zlib level:1`（重速度），若改为 level 6 会更慢但文件更小，未测。
