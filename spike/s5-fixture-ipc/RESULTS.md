# S5 结论报告 — 1000 万行 fixture + 列式 IPC 首屏实测

> Spike 性质：决策性（影响 v1.0 排期）。所有数字均为本机实测，非估算。
> 环境：macOS 27.0 / Apple M5 Pro 15 核 / 48GB / arm64 · Node v22.22.2 · MySQL 8.0.46（Docker arm64）· 宿主端口 13306。
> 连接参数严格按 TECH-REVIEW §4.4：`supportBigNumbers/bigNumberStrings/dateStrings/jsonStrings:true`、`decimalNumbers:false`、`timezone:'local'`、`multipleStatements:false`、`rowsAsArray:true`。
> 测量方式：`performance.now()`，每场景 5~7 次取 P50；渲染侧解码用 Node 模拟，真实 Electron 内走 `postMessage(payload, transferList)` 零拷贝（transfer≈0）。

## 二、列式 vs JSON 对照表（P50，实测）

每个场景同批数据分别走列式编码与 `JSON.stringify/parse`，量编码 ms / 体积 / 解码 ms。

| 场景 | 形式 | 体积 | 编码 ms | 全量解码 ms | **只解可视区 40 行 ms** |
|---|---|---|---|---|---|
| LIMIT 3000（表首屏） | 列式 | 0.477 MB | 4.15 | 1.53 | **0.029** |
| | JSON | 0.443 MB | 0.70 | 1.10 | 必须全量 1.10 |
| LIMIT 10000（结果集） | 列式 | 1.602 MB | 12.91 | 5.44 | **0.028** |
| | JSON | 1.492 MB | 2.44 | 3.98 | 必须全量 3.98 |
| LIMIT 200000（补充） | 列式 | 33.20 MB | 338.7 | 132.3 | **0.029** |
| | JSON | 31.32 MB | 50.5 | 178.4 | 必须全量 178.4 |
| LIMIT 500000（补充） | 列式 | 83.58 MB | 981.8 | 327.8 | **0.029** |
| | JSON | 78.99 MB | 186.1 | 338.3 | 必须全量 338.3 |

**关键对照（LIMIT 3000）**：列式比 JSON **省 −0.034 MB**、编码**慢 3.45 ms**；但只解 40 行省 **~1.07 ms**（JSON 被迫全量解析）。

### ⚠️ 决策性发现（请产品/架构关注）
在 PRD 指定的规模（3k / 1万行、12 列紧凑数据）下：
- **列式体积并不更小**（0.477 vs 0.443 MB），且**编码反而比 `JSON.stringify` 慢 ~3~5 倍**。原因：紧凑小数值在 JSON 里按文本只占 1~7 字节，而列式固定 8 字节数值 + 4 字节偏移。
- 列式的真正价值**不在本规模的"体积/编码速度"**，而在两点：
  1. **只解可视区**：解码 40 行恒定 ~0.03 ms，与结果集大小无关；JSON 必须全量 parse，到 50 万行已涨到 **338 ms**。
  2. **渲染端内存有界**：无需在渲染进程里展开成完整对象数组（50 万行 JSON 全量解析 ≈ 338 ms 且峰值内存翻倍）。
- **结论**：PRD §2.2 的列式方案**应保留**（与 S1 网格虚拟滚动天然契合），但其论证依据应从"省体积/省序列化"修正为"**按需解码可视区 + 内存有界 + 大结果集可扩展**"。TECH-REVIEW 给出的"15MB→2~4MB"仅在更宽/更长文本的结果集才成立。

## 三、三项预算判定（实测链路分解）

链路 = 连接获取 + 服务端执行 + 列式编码 + 模拟 IPC(零拷贝) + 解码可视区 40 行。

### 1) 表首屏 ≤1000ms —— ✅ 可达
| 分解项 | 实测 ms |
|---|---|
| 连接获取（pool 热） | 0.04 |
| `SELECT * FROM big_table LIMIT 3000` 服务端执行 | 4.14 |
| 列式编码 | 4.15 |
| IPC transfer（零拷贝） | ≈0 |
| 解码前 40 行 | 0.03 |
| **合计** | **8.4 ms** |

判定：**可达**（预算 1000ms，实测 8.4ms，余量 ~992ms）。
> 注：此为纯数据层耗时（localhost）。真实 Electron 路径还含主/渲染进程启动、React 提交 40 行等，但数据层仅占 8ms，余量充足。

### 2) SQL 执行结果首行渲染 ≤500ms（不含查询本身）—— ✅ 可达
- 1 万行结果集：列式编码 12.91 ms + 解码 40 行 0.03 ms = **12.9 ms**。
- 判定：**可达**（预算 500ms，实测 12.9ms）。JSON 对照组全量解析需 3.98 ms，也达标，但列式在更大结果集下优势放大。

### 3) 带索引字段排序 ≤1500ms —— ✅ 可达
- `ORDER BY created_at DESC LIMIT 3000`：`EXPLAIN` 确认命中 `idx_created_at`（Backward index scan，仅扫描 3000 行）。
| 分解项 | 实测 ms |
|---|---|
| 服务端执行（索引倒序扫描） | 4.02 |
| 列式编码 | 2.91 |
| 解码 40 行 | 0.02 |
| **合计** | **6.9 ms** |

- 判定：**可达**（预算 1500ms，实测 6.9ms）。

> 无索引全表排序不在预算范围内（PRD 明确"带索引字段"），不测。

## 四、数据正确性抽查（§八 红线，全部通过 ✅）

种子里故意放入边界值（id `9007199254740993/994/995`），连接参数严格按 §4.4。

| 验收项 | 抽查值 | 结果 |
|---|---|---|
| BIGINT > 2^53 精确（列式编码/解码后） | 入 `9007199254740993` → 出 `9007199254740993` | ✅ 通过 |
| `DATETIME(6)` 微秒不丢（`dateStrings` 原文） | `2026-09-21 12:34:56.123456` → 原样 | ✅ 通过 |
| JSON 字段内大整数不被二次解析（`jsonStrings`） | `{"id": 9007199254740993, "name": "x"}` 原文保留 | ✅ 通过 |
| DECIMAL 保持字符串、无浮点尾数 | `1234567890.12` → 字符串原样 | ✅ 通过 |
| nullMask（deleted_at 可为 NULL） | 行1=NULL、行2=`2026-09-20 00:00:00.000000` | ✅ 通过 |

## 五、修正建议值

三项预算**均可达**，无需下调 PRD 数值。但给出两条工程建议（非预算修正）：
1. **列式方案论证修正**：保留列式 IPC，但价值主张改为"按需解码可视区 + 渲染内存有界"，而非"更小更快"——本规模下体积与编码速度列式并不占优。
2. **大结果集风险预警**：JSON 全量解析在 50 万行已达 338 ms，若未来默认加载行数上调（如 Q16 放开到 1 万以上且不做可视区解码），首屏会劣化；列式 + 只解可视区是该风险的对冲。

## 六、复现步骤

```bash
cd spike/s5-fixture-ipc
docker compose up -d            # 起 MySQL（宿主 13306，卷 dbstudio_mysql_data）
# 等 healthy（约 20s）
npm i mysql2                    # 仅本目录安装
node seed/seed.mjs              # 造 1000 万行 fixture（≈2.5min，卷持久化）
node bench-ipc.mjs              # 跑对照/链路/正确性，写 raw/bench-raw.json
```

后续复跑性能测试只需 `docker compose up -d` + `node bench-ipc.mjs`（fixture 已在卷里，不必重新造数）。
