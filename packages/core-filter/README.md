# @dbstudio/core-filter

筛选构建器 —— 图形化条件 → 参数化 WHERE。

> 依据：PRD §6.3.3

## 三条硬约束

1. **值一律 `?` 占位绑定，绝不拼进字符串**。用户在值框里输入什么，都只是参数。
2. **标识符走 `quoteIdentifier`**。
3. **可预览**：产出的 `preview` 是给用户看的条件原文，UI 展示它，
   不要自己再拼一遍 —— Navicat 的"长条件显示不下也加不了条件"正是预览不可编辑的后果。

## 操作符按字段类型动态变化

| 字段 | 操作符 |
|---|---|
| 数值 / 日期 | 等于·不等于·范围比较·介于·属于·NULL 判定（**无"包含"**） |
| 文本 / ENUM / SET / JSON | 再加 包含·不包含·开头·结尾·正则 |
| BLOB / 二进制 / 几何 | **只有 IS NULL / IS NOT NULL** |
| 未知类型 | 最保守集合（宁可少给，也不给会出错的） |

## 不完整的条件：静默跳过，不抛异常

字段名空 / BETWEEN 只填了一半 / IN 没有候选值 → 跳过该条件，不生成半截 SQL。
这比抛异常更符合筛选器的交互 —— **用户是边填边看的**。

⚠️ 一条容易写反的规则：单值操作符的空串是**有意义**的输入（查空串 `''`），
所以不能用空串判"没填完"。只有 `undefined / null`（用户根本没碰过输入框）才算没填。
BETWEEN 的两个端点则要求非空。两者规则不同，别统一处理。

## 参数顺序（真库踩过的坑）

`buildOpenTableSql()` 生成的 SQL 里 WHERE 在 LIMIT 之前，
所以**参数必须是 `[...whereParams, ...limitParams]`**。
反了会把 `'paid'` 喂给 `LIMIT`，报 `near ''30''` 这类莫名其妙的语法错误。
